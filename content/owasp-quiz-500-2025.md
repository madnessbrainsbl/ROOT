# Квиз по OWASP Top 10:2025 — 500 вопросов (по 50 на категорию)

Формат: вопрос → 4 варианта (A–D) → правильный ответ. Для практических/спорных вопросов — краткое пояснение.

---

## A01:2025 — Broken Access Control (50 вопросов)

1. Что из перечисленного НЕ относится к Broken Access Control в OWASP Top 10:2025? A) IDOR B) SQL Injection C) BFLA D) CSRF
   Ответ: **B** (SQL Injection относится к Injection (A05), а не к Broken Access Control. IDOR, BFLA и CSRF — это сбои контроля доступа, входящие в A01:2025.)

2. Какой CWE соответствует Server-Side Request Forgery в редакции 2025 года? A) CWE-352 B) CWE-601 C) CWE-918 D) CWE-862
   Ответ: **C** (CWE-918 — стандартный идентификатор для Server-Side Request Forgery. В OWASP Top 10:2025 SSRF включён в A01 Broken Access Control, а не выделен отдельной категорией.)

3. IDOR расшифровывается как: A) Internal Denial of Resource B) Insecure Direct Object Reference C) Internal Data Object Retrieval D) Indirect Direct Object Request
   Ответ: **B** (IDOR расшифровывается как Insecure Direct Object Reference: доступ к объекту по id из запроса без проверки, что вызывающий имеет право на этот объект.)

4. Принцип «deny by default» означает: A) все запросы логируются B) доступ разрешён только явно указанным ролям, всё остальное запрещено C) все ошибки скрываются от пользователя D) сервер отклоняет TLS 1.0
   Ответ: **B** (Принцип «deny by default» означает: доступ только явно разрешённым ролям или правам, всё остальное запрещено. Логирование или сокрытие ошибок этот принцип не реализуют.)

5. BFLA — это: A) Broken Function Level Authorization B) Basic File Level Access C) Backend Function Logic Attack D) Broken Field Level Auth
   Ответ: **A** (BFLA — Broken Function Level Authorization: отсутствует или неверна проверка, что вызывающий может выполнять привилегированную функцию (например admin API).)

6. Почему проверка прав доступа только на фронтенде (скрытие кнопки в UI) не считается контролем доступа? A) Это слишком медленно B) JS нельзя тестировать C) Атакующий может напрямую обратиться к API/эндпоинту в обход UI D) Браузеры блокируют такие проверки
   Ответ: **C** (Проверки только в UI — не enforcement: атакующий вызывает тот же API через curl или прокси, обходя скрытую кнопку. Контроль доступа должен выполняться на доверенном сервере.)

7. Какой HTTP-статус-код различие (403 vs 404) может помочь атакующему в энумерации ресурсов? A) Позволяет узнать версию сервера B) Позволяет отличить «ресурс существует, но нет доступа» от «ресурса нет» C) Указывает на использование WAF D) Не имеет значения для access control
   Ответ: **B** (Ответ 403 для существующих запрещённых ресурсов и 404 только для отсутствующих позволяет перечислять, что есть. Единообразные ответы снижают перечисление (утечки в духе CWE-200).)

8. Что такое force browsing (CWE-425)? A) Автоматическое обновление браузера B) Угадывание/перебор URL страниц без ссылок в UI C) Принудительный редирект D) DDoS через браузер
   Ответ: **B** (Force browsing (CWE-425) — угадывание или запрос URL без ссылок в UI, чтобы добраться до скрытых admin-страниц или файлов без серверной авторизации.)

9. Уязвимость CORS-мисконфигурации возникает, когда: A) сервер вообще не поддерживает CORS B) Access-Control-Allow-Origin отражает любой Origin вместе с Allow-Credentials: true C) используется HTTPS D) отсутствует Content-Type заголовок
   Ответ: **B** (Отражение любого Origin вместе с Access-Control-Allow-Credentials: true позволяет вредоносному сайту читать аутентифицированные cross-origin ответы — классический сбой CORS.)

10. Атрибут cookie, отсутствие которого попало в список CWE категории A01:2025 (CWE-1275): A) Secure B) HttpOnly C) SameSite D) Max-Age
    Ответ: **C** (CWE-1275 относится к отсутствию атрибута SameSite у cookie. Без SameSite (и смежных защит от CSRF) браузер может слать session cookie в cross-site запросах, что ведёт к CSRF в A01.)

11. Атакующий модифицирует JWT, меняя alg на "none". Какой класс уязвимости это эксплуатирует? A) Cryptographic Failure B) Отсутствие проверки подписи токена на сервере (Broken Access Control) C) Injection D) Insecure Design
    Ответ: **B** (Принятие JWT с alg=none (или пропуск проверки подписи) — отсутствие серверной проверки целостности токена: подмена метаданных в Broken Access Control, а не «чистый» крипто-провал.)

12. CSRF-атака требует от атакующего: A) знания пароля жертвы B) чтобы жертва была аутентифицирована и выполнила действие через подготовленный запрос без ведома C) физического доступа к устройству жертвы D) MITM-позиции в сети
    Ответ: **B** (CSRF использует автоматическую отправку браузером сессии жертвы на сайт, где она уже вошла; пароль не нужен, если session cookie уходит с подготовленным запросом.)

13. Какой заголовок/механизм — основная защита от CSRF наряду с anti-CSRF токеном? A) X-Frame-Options B) SameSite cookie атрибут C) Content-Security-Policy D) X-Content-Type-Options
    Ответ: **B** (Помимо anti-CSRF токенов, атрибут SameSite у cookie ограничивает отправку cookie в cross-site запросах и является основной browser-side защитой от CSRF в контексте A01.)

14. Path Traversal (CWE-22) чаще всего эксплуатируется через: A) SQL-запрос B) последовательности вида ../../../etc/passwd в параметрах, обрабатывающих пути к файлам C) XML-парсер D) HTTP-заголовок Referer
    Ответ: **B** (Path Traversal (CWE-22) внедряет сегменты вида ../ в параметры пути, чтобы сервер читал файлы вне допустимого каталога (например /etc/passwd).)

15. Confused Deputy (CWE-441) в контексте Broken Access Control описывает ситуацию, когда: A) пользователь путает логин и пароль B) привилегированный компонент обманом заставляют выполнить действие от имени менее привилегированного атакующего C) два администратора конфликтуют в правах D) сертификат истёк
    Ответ: **B** (Confused Deputy (CWE-441) — привилегированный компонент действует по входным данным атакующего и выполняет действия, которые атакующий сам сделать не мог.)

16. Почему SSRF в 2025 включили в категорию Broken Access Control, а не оставили отдельной категорией? A) SSRF устарела как класс B) По сути SSRF — нарушение контроля доступа сервера к внутренним ресурсам C) SSRF больше не встречается D) Так решило голосование сообщества без обоснования
    Ответ: **B** (В 2025 OWASP рассматривает SSRF как обман сервера: он обращается к внутренним ресурсам, недоступным атакующему — сбой контроля доступа к server-side reachability, а не отдельный ранг Top 10.)

17. Типичная цель SSRF-атаки в облачной инфраструктуре: A) обход CAPTCHA B) cloud metadata endpoint (например, 169.254.169.254) C) DNS-сервер провайдера D) NTP-сервер
    Ответ: **B** (Cloud metadata (часто 169.254.169.254) хранит credentials и конфигурацию; SSRF до этого endpoint — критичный обход контроля доступа к внутренним ресурсам.)

18. Какая техника позволяет обойти SSRF allow-list, основанный на проверке домена, а не итогового IP? A) DNS rebinding B) Base64-кодирование C) Increment ID D) XML entity expansion
    Ответ: **A** (DNS rebinding сначала резолвит имя в разрешённый IP, затем — во внутренний, обходя SSRF allow-list, который проверяет только домен, а не итоговый IP.)

19. Пентестер тестирует IDOR. Какая методика наиболее эффективна? A) Только сканирование портов B) Замена ID/UUID в запросе на значение, полученное в другой (чужой) сессии C) Проверка версии TLS D) Brute-force пароля
    Ответ: **B** (Эффективный тест IDOR — подмена идентификаторов объектов между сессиями (или tenant) при той же аутентификации, доказывая отсутствие проверки владения.)

20. Вертикальная эскалация привилегий отличается от горизонтальной тем, что: A) вертикальная — доступ user → admin, горизонтальная — доступ к данным другого пользователя того же уровня B) вертикальная работает только в мобильных приложениях C) горизонтальная невозможна без MFA D) разницы нет
    Ответ: **A** (Вертикальная эскалация повышает уровень прав (user → admin); горизонтальная остаётся на той же роли, но даёт доступ к ресурсам другого пользователя.)

21. Согласно данным OWASP 2025, какой процент протестированных приложений содержал хотя бы один CWE из категории Broken Access Control? A) 25% B) 50% C) 73% D) 100%
    Ответ: **D** (По данным OWASP Top 10:2025, 100% протестированных приложений имели хотя бы один CWE из Broken Access Control — наиболее распространённая категория.)

22. Что из перечисленного — правильная практика реализации access control согласно OWASP? A) Реализовывать проверку прав в каждом контроллере заново B) Реализовать единожды и переиспользовать во всём приложении C) Полагаться на скрытие эндпоинтов (security through obscurity) D) Хранить права доступа в cookie без подписи
    Ответ: **B** (OWASP рекомендует единую переиспользуемую точку авторизации вместо копипасты, security through obscurity или хранения прав в клиентских/неподписанных данных.)

23. CWE-566 из списка A01:2025 описывает: A) XSS через SQL B) Authorization Bypass Through User-Controlled SQL Primary Key C) Слабый TLS шифр D) Утечку памяти
    Ответ: **B** (CWE-566 — Authorization Bypass Through User-Controlled SQL Primary Key: клиентский primary key попадает в SQL без проверки владения/авторизации.)

24. Инструмент Burp Suite при тестировании access control чаще всего используется для: A) фаззинга памяти B) перехвата и модификации запросов (замена параметров, ролей, токенов) вручную/через Intruder C) статического анализа кода D) сканирования Wi-Fi
    Ответ: **B** (Proxy и Intruder в Burp Suite позволяют менять id, роли, методы и токены и доказывать отсутствие серверной авторизации — основа тестирования access control.)

25. Почему стейтфул session ID нужно инвалидировать на сервере при логауте? A) Чтобы уменьшить объём БД B) Чтобы украденный/оставшийся в браузере токен нельзя было переиспользовать после выхода C) Это требование GDPR напрямую D) Не требуется, если используется HTTPS
    Ответ: **B** (Если сервер принимает сессию после logout, оставшийся или украденный session id остаётся рабочим. Инвалидация на сервере завершает сессию на доверенной стороне.)

26. Какая из мер — НЕ относится к предотвращению Broken Access Control? A) Rate limiting на чувствительные эндпоинты B) Логирование отказов авторизации C) Хранение паролей через bcrypt D) Модель прав на основе владения записью (record ownership)
    Ответ: **C** (Хранение паролей с bcrypt — криптографическая мера (A04 Cryptographic Failures), а не mitigation для Broken Access Control. Rate limiting, логирование отказов и ownership — защиты A01.)

27. Directory listing (CWE-548), включённый на веб-сервере, может привести к: A) улучшению SEO B) раскрытию структуры файлов и потенциально чувствительных файлов посторонним C) увеличению производительности D) автоматическому шифрованию трафика
    Ответ: **B** (Включённый directory listing (CWE-548) раскрывает структуру файлов и путей и может обнажить бэкапы, конфиги и другие чувствительные данные.)

28. Open Redirect (CWE-601) обычно используется атакующим для: A) DoS-атаки B) фишинга — переход по легитимной ссылке домена жертвы с редиректом на вредоносный сайт C) SQL-инъекции D) обхода WAF по IP
    Ответ: **B** (Open Redirect (CWE-601) чаще всего для фишинга: URL на доверенном домене перенаправляет на вредоносный сайт, повышая доверие к приманке.)

29. Что означает «Authorization Bypass Through User-Controlled Key» (CWE-639)? A) Слабый криптографический ключ B) Приложение использует значение, присланное клиентом, как ключ доступа к записи без проверки принадлежности C) Утечка API-ключа в git D) Использование дефолтного пароля
    Ответ: **B** (CWE-639: приложение берёт ключ из запроса (id, путь и т.п.) для доступа к записи и не проверяет владение/права аутентифицированного пользователя — классический IDOR/BOLA.)

30. Zero Trust архитектура относится к Broken Access Control тем, что: A) отменяет необходимость аутентификации B) предполагает проверку прав на каждом запросе, не доверяя факту нахождения «внутри периметра» C) заменяет TLS D) не связана с access control
    Ответ: **B** (Zero Trust не доверяет «нахождению внутри периметра»: каждый запрос проверяется на аутентификацию и авторизацию — напрямую против паттернов Broken Access Control.)

31. Симптом «An accessible API with missing access controls for POST, PUT и DELETE» означает: A) GET-запросы защищены проверкой прав, а модифицирующие методы — нет B) API вообще не работает C) отсутствие HTTPS D) отсутствие документации Swagger
    Ответ: **A** (Защита только GET при открытых POST/PUT/DELETE — неполная method-level авторизация: чтение ограничено, а изменяющие операции — нет.)

32. Классический пример из OWASP-документации: атакующий меняет параметр acct в URL запроса к своему счёту на чужой. Это пример: A) CSRF B) IDOR C) XSS D) SSRF
    Ответ: **B** (Подмена параметра acct (или аналогичного id) на чужое значение без проверки владения — классический пример IDOR / Insecure Direct Object Reference.)

33. Какая проверка НЕ является достаточной защитой от access control атак: A) серверная проверка роли на каждый запрос B) скрытие ссылки в интерфейсе (UI-only) C) проверка владения записью в domain-модели D) rate limiting + логирование отказов
    Ответ: **B** (Скрытие ссылки меняет только UX; endpoint может остаться доступным прямым запросом. Реальная защита — серверная авторизация, ownership и мониторинг отказов.)

34. Метаданные .git, оставленные в веб-корне (CWE-538), опасны, потому что: A) увеличивают время загрузки страницы B) могут раскрыть историю коммитов, включая случайно закоммиченные секреты C) вызывают XSS D) блокируют индексацию поисковиками
    Ответ: **B** (Доступные .git-метаданные (CWE-538) могут отдать историю коммитов и содержимое, включая секреты, которые когда-то попали в репозиторий.)

35. Что из перечисленного — пример горизонтальной privilege escalation? A) Обычный пользователь получает права администратора B) Пользователь A читает личные сообщения пользователя B, имея тот же уровень доступа C) Гостевой доступ отключается D) Смена пароля администратора
    Ответ: **B** (Горизонтальная эскалация — злоупотребление на том же уровне прав: доступ к данным другого пользователя (например чужие сообщения). Получение admin — вертикальная.)

36. Почему короткоживущие JWT в паре с refresh-токеном предпочтительнее долгоживущих JWT? A) Уменьшают вычислительную нагрузку сервера B) Сокращают окно, в течение которого украденный access-токен остаётся валидным C) JWT иначе не поддерживает подпись D) Требование стандарта HTML5
    Ответ: **B** (Короткоживущие access JWT быстро истекают при краже; refresh-токены можно ротировать и отзывать, сокращая окно действия скомпрометированного access token.)

37. Разница между Missing Authorization (CWE-862) и Incorrect Authorization (CWE-863): A) первое — проверка вообще отсутствует, второе — проверка есть, но реализована неверно B) это синонимы C) первое относится только к API D) второе относится только к базам данных
    Ответ: **A** (CWE-862 Missing Authorization — проверки нет вообще; CWE-863 Incorrect Authorization — проверка есть, но логика или политика неверны.)

38. При аудите CORS-политики нужно проверить в первую очередь: A) версию Node.js B) отражается ли произвольный Origin в Access-Control-Allow-Origin вместе с Allow-Credentials: true C) размер cookie D) наличие robots.txt
    Ответ: **B** (Ключевая проверка CORS: отражается ли произвольный Origin вместе с Allow-Credentials: true, что даёт credentialed cross-origin кражу данных.)

39. UNIX Symlink Following (CWE-61) — это уязвимость, при которой: A) приложение неправильно обрабатывает символические ссылки, что позволяет получить доступ к файлам вне ожидаемой директории B) сервер зависает при большом трафике C) браузер не поддерживает JS D) TLS-сертификат просрочен
    Ответ: **A** (UNIX Symlink Following (CWE-61) — небезопасная обработка символических ссылок, из-за которой приложение читает или пишет файлы вне допустимого каталога.)

40. Согласно OWASP, «Modeling access controls should enforce _____ rather than allowing users to CRUD any record» — пропущенное слово: A) role hierarchy B) record ownership C) IP whitelisting D) session duration
    Ответ: **B** (OWASP подчёркивает enforcement владения записью (record ownership), чтобы пользователь не мог CRUD произвольные записи только зная id.)

41. Как правильнее всего протестировать BFLA для эндпоинта /admin/deleteUser? A) Проверить, что кнопка недоступна обычному пользователю в UI B) Отправить прямой HTTP-запрос от имени low-priv пользователя напрямую (curl/Burp), минуя UI C) Проверить логи сервера D) Прочитать документацию API
    Ответ: **B** (BFLA доказывается прямым вызовом привилегированной функции от low-priv пользователя (curl/Burp). Скрытие кнопки в UI не доказывает серверный отказ.)

42. Какой из перечисленных методов атаки НЕ относится к Broken Access Control? A) Parameter tampering B) Time-based blind SQL injection C) JWT alg=none D) Force browsing
    Ответ: **B** (Time-based blind SQL injection — техника Injection (A05). Parameter tampering, JWT alg=none и force browsing относятся к контролю доступа.)

43. Использование ролевой модели (RBAC) само по себе гарантирует отсутствие Broken Access Control? A) Да, всегда B) Нет — плохая реализация проверки роли на сервере всё равно может быть уязвима C) Да, если используется JWT D) Да, если приложение написано на Java
    Ответ: **B** (RBAC помогает только если роли корректно проверяются на сервере на каждом чувствительном пути. Модель без правильного enforcement всё равно даёт Broken Access Control.)

44. Что из перечисленного — правильный порядок действий при обнаружении IDOR на пентесте? A) Сразу публиковать в соцсетях B) Задокументировать PoC, оценить impact (какие данные доступны), сообщить по программе ответственного разглашения/bug bounty C) Массово скачать данные всех пользователей для «доказательства» D) Игнорировать, если severity низкий
    Ответ: **B** (Этичный процесс: PoC, оценка impact и отчёт через responsible disclosure/bug bounty — без публичных сливов и массовой выгрузки чужих данных.)

1. Сколько CWE входит в категорию A05:2025 — наибольшее число среди всех категорий? A) 16 B) 24 C) 38 D) 40
   Ответ: **C** (По данным OWASP Top 10:2025 категория A05 Injection включает наибольшее число CWE — 38, что отражает широту семейства инъекций (SQL, XSS, command, SSTI и др.).)

2. Root cause категории Injection — это: A) слабый пароль B) отсутствие разделения между control plane и data plane при построении запроса/команды (конкатенация вместо параметризации) C) отсутствие HTTPS D) неправильная конфигурация сервера
   Ответ: **B** (Корневая причина Injection — смешивание данных и управляющих инструкций: пользовательский ввод конкатенируется в запрос/команду вместо параметризации. Поэтому payload может изменить структуру или семантику операции.)

3. Какой тип SQL-инъекции определяется по разнице во времени ответа сервера? A) UNION-based B) Error-based C) Time-based blind D) Stacked queries
   Ответ: **C** (Time-based blind SQL Injection выявляется по задержке ответа (например, SLEEP/WAITFOR), когда данные и ошибки не отражаются напрямую. Разница во времени подтверждает выполнение условия в СУБД.)

4. Boolean-based blind SQL Injection определяется через: A) вывод текста ошибки СУБД B) разницу в содержимом/поведении отклика при истинном/ложном условии запроса C) время ответа сервера D) HTTP-заголовки
   Ответ: **B** (Boolean-based blind SQLi опирается на изменение содержимого или поведения ответа при истинном и ложном условии, а не на текст ошибки или паузу. По разнице ответов атакующий побитово извлекает данные.)

5. Second-order SQL Injection — это ситуация, когда: A) инъекция срабатывает мгновенно при вводе B) вредоносный payload сохраняется в БД и срабатывает позже при использовании в другом запросе C) инъекция работает только через второй параметр D) инъекция требует двух пользователей одновременно
   Ответ: **B** (Second-order SQL Injection: payload сохраняется «безопасно», а затем подставляется в другой запрос без параметризации и срабатывает позже. Поэтому недостаточно проверять только точку ввода.)

6. SSTI (Server-Side Template Injection) чаще всего приводит к: A) XSS только B) DoS только C) RCE — инъекция в шаблонизатор (Jinja2, Twig, FreeMarker) позволяет выполнить произвольный код на сервере D) утечке cookie только
   Ответ: **C** (SSTI даёт выполнение доступ к API шаблонизатора (Jinja2, Twig, FreeMarker), что часто приводит к RCE на сервере, а не только к XSS. Это серверная инъекция управляющей логики шаблона.)

7. Payload {{7*7}} в поле ввода используется для тестирования: A) SQL Injection B) SSTI (если в отклике появится 49 — шаблонизатор уязвим) C) XSS D) LDAP Injection
   Ответ: **B** (Payload {{7*7}} — классический пробник SSTI: если в ответе появляется 49, сервер вычислил выражение шаблона. Это отличает SSTI от простого отражения текста.)

8. Reflected XSS отличается от Stored XSS тем, что: A) reflected сохраняется в БД навсегда B) reflected срабатывает немедленно из параметров запроса и требует, чтобы жертва перешла по специальной ссылке, тогда как stored сохраняется на сервере и поражает всех посетителей страницы C) reflected работает только в Internet Explorer D) это одно и то же
   Ответ: **B** (Reflected XSS срабатывает сразу из параметров текущего запроса и обычно требует, чтобы жертва открыла вредоносную ссылку. Stored XSS сохраняется на сервере и поражает последующих посетителей страницы.)

9. DOM-based XSS отличается от Reflected/Stored тем, что: A) вообще не существует B) уязвимость реализуется полностью на стороне клиента через небезопасную работу JS с DOM, без участия сервера в отражении payload C) требует SQL-базы D) работает только через cookies
   Ответ: **B** (DOM-based XSS возникает целиком на клиенте: небезопасный JS читает untrusted данные и пишет их в DOM, даже если сервер payload не «отражал» в HTML. Защита — безопасные API DOM и контекстное экранирование на клиенте.)

10. NoSQL Injection в MongoDB часто эксплуатируется через операторы вида: A) UNION SELECT B) $where, $ne в JSON-параметрах C) LDAP filter syntax D) XPath expressions
    Ответ: **B** (NoSQL-инъекции в MongoDB часто используют операторы вроде $ne и $where в JSON-параметрах, меняя логику запроса. Классический UNION SELECT здесь не применим.)

11. OS Command Injection возникает, когда: A) пользовательский ввод напрямую передаётся в системный вызов (exec/system/backticks) без санитизации C) используется устаревший TLS D) отсутствует rate limiting
    Ответ: **A** (OS Command Injection возникает, когда ввод пользователя передаётся в shell/system API без разделения аргументов и экранирования. Тогда спецсимволы shell могут запустить произвольные команды.)

12. Параметризованные запросы (prepared statements) защищают от SQL Injection, потому что: A) шифруют запрос B) СУБД заранее компилирует структуру запроса отдельно от данных, поэтому пользовательский ввод не может изменить логику запроса C) ускоряют выполнение запроса D) требуют меньше памяти
    Ответ: **B** (Prepared statements компилируют структуру SQL отдельно от значений параметров, поэтому ввод не может изменить синтаксис запроса. Данные остаются данными, а не частью control plane.)

13. Контекстно-зависимое экранирование вывода для XSS означает: A) одно универсальное экранирование подходит для всех случаев B) способ экранирования различается в зависимости от места вставки данных в DOM (HTML-тег, атрибут, JS-строка, URL) C) экранирование не требуется при использовании HTTPS D) достаточно только серверной валидации ввода
    Ответ: **B** (Контекстное экранирование XSS выбирает правила под место вставки: HTML-текст, атрибут, JS-строка, URL — у каждого свой набор опасных символов. Универсальный «escape HTML» часто недостаточен.)

14. CSP (Content-Security-Policy) снижает риск XSS, потому что: A) полностью устраняет XSS без других мер B) ограничивает источники, из которых браузер может исполнять скрипты, работая как defense-in-depth даже при наличии XSS-инъекции C) шифрует cookie D) блокирует SQL-запросы
    Ответ: **B** (CSP ограничивает источники и способы исполнения скриптов в браузере и служит defense-in-depth даже при наличии XSS. Сама по себе она не заменяет корректное экранирование вывода.)

15. CRLF Injection (Header Injection) может привести к: A) SQL-инъекции B) HTTP response splitting и связанным атакам (например, кэш-poisoning, XSS через заголовки) C) утечке памяти D) DoS через переполнение буфера
    Ответ: **B** (CRLF/Header Injection позволяет внедрять переводы строк в HTTP-заголовки, что ведёт к response splitting, cache poisoning и XSS через подмену ответа. Нужна валидация и запрет CR/LF во вводе для заголовков.)

16. XXE (XML External Entity) относится к инъекции, потому что: A) вредоносный XML-документ определяет внешнюю сущность, которую парсер разрешает и обрабатывает, что может привести к чтению файлов/SSRF C) требует SQL-базы D) работает только в PDF
    Ответ: **A** (XXE — инъекция через определение внешних сущностей в XML: парсер разрешает entity и может раскрыть файлы или вызвать SSRF. Поэтому XXE относят к классу Injection.)

17. LDAP Injection эксплуатирует: A) неправильную сборку LDAP-фильтра из непроверенного пользовательского ввода B) слабость TLS C) отсутствие MFA D) переполнение буфера
    Ответ: **A** (LDAP Injection эксплуатирует сборку LDAP-фильтра из непроверенного ввода, меняя условие поиска/аутентификации. Нужны экранирование спецсимволов LDAP и параметризация фильтров.)

18. Почему ORM не является 100% защитой от инъекций? A) ORM никогда не подвержены инъекциям B) При неаккуратном использовании (например, raw-запросы внутри ORM, построение фильтров через конкатенацию строк) ORM всё равно может быть уязвим C) ORM полностью заменяет базу данных D) ORM работает только с NoSQL
    Ответ: **B** (ORM не гарантирует защиту, если используются raw-запросы, конкатенация в фильтрах или native SQL. При неверном использовании control plane снова смешивается с данными.)

19. UNION-based SQL Injection используется атакующим для: A) изменения структуры таблицы B) объединения результата вредоносного SELECT-запроса с результатом легитимного запроса для извлечения данных из других таблиц C) удаления таблицы D) шифрования базы данных
    Ответ: **B** (UNION-based SQLi объединяет вредоносный SELECT с результатом легитимного запроса, чтобы вытащить данные из других таблиц. Число и типы колонок должны совпадать с исходным SELECT.)

20. OGNL/SpEL injection (например, в Struts2/Spring) относится к подтипу: A) SQL Injection B) Expression Language / Command Injection, часто приводящему к RCE C) XSS D) CSRF
    Ответ: **B** (OGNL/SpEL injection — это инъекция expression language, часто ведущая к RCE в экосистемах Java (Struts2, Spring). Это подтип Expression Language / Command Injection, а не классический SQL.)

21. Диапазон impact для категории Injection в OWASP описывается как: A) от низкого до критичного одинаково для всех подтипов B) от high-frequency/low-impact (например, часть XSS) до low-frequency/high-impact (например, SQLi) C) всегда критичный D) всегда низкий
    Ответ: **B** (По OWASP влияние Injection варьируется: от частых, но часто ограниченных XSS до более редких, но высоковлиятельных SQLi/RCE. Категория охватывает оба полюса риска.)

22. Позитивная валидация ввода (allow-list) предпочтительнее негативной (deny-list, блэклист специальных символов), потому что: A) allow-list проще в реализации технически B) allow-list определяет точно разрешённый формат, тогда как deny-list легко обойти новыми/непредвиденными техниками обхода C) deny-list быстрее работает D) они эквивалентны по эффективности
    Ответ: **B** (Allow-list задаёт точный допустимый формат ввода, тогда как deny-list легко обходится новыми вариантами payload. Для инъекций positive validation предпочтительнее negative.)

    Ответ: **A** (Корректный тест time-based blind SQLi — payload с SLEEP/задержкой и измерение времени ответа. Заметная пауза при истинном условии подтверждает выполнение.)

24. Ограничение прав учётной записи БД приложения (read-only там, где не нужна запись) относится к принципу: A) defense in depth / least privilege — снижает impact успешной инъекции даже при её наличии B) не связано с injection C) требуется только для NoSQL D) заменяет необходимость параметризации
    Ответ: **A** (Урезание привилегий учётки приложения в БД — least privilege / defense in depth: даже при успешной инъекции ущерб ограничен. Это не устраняет root cause, но снижает impact.)

25. Почему статический анализ кода (SAST) полезен для поиска инъекций? A) SAST может автоматически исправлять код B) SAST может обнаружить паттерны конкатенации пользовательского ввода в запросах/командах на этапе разработки, до продакшена C) SAST заменяет пентест полностью D) SAST работает только с скомпилированным кодом
    Ответ: **B** (SAST находит паттерны слияния untrusted input с sink’ами (запросы, команды) ещё на этапе разработки. Это помогает закрыть инъекции до продакшена, когда DAST ещё недоступен.)

26. Атрибут HttpOnly для cookie снижает риск: A) SQL Injection B) кражи cookie через XSS (JS не может прочитать HttpOnly cookie) C) CSRF D) SSTI
    Ответ: **B** (Флаг HttpOnly запрещает JavaScript читать cookie, снижая кражу сессии через XSS. Он не предотвращает сам XSS и не защищает от CSRF.)

27. Что из перечисленного — пример mutation-based XSS (mXSS)? A) Payload напрямую отражается без изменений B) Браузер при парсинге/санитизации HTML трансформирует «безопасный» на вид input в исполняемый код из-за особенностей парсера C) SQL-запрос с UNION D) LDAP-фильтр
    Ответ: **B** (mXSS — когда браузер при парсинге/«очистке» HTML переписывает, казалось бы, безопасную разметку в исполняемый код. Классические санитайзеры без учёта мутаций парсера могут пропустить это.)

28. Почему инъекция через файл-загрузку (например, filename с '; DROP TABLE...) тоже относится к A05? A) Загрузка файлов не связана с injection B) Метаданные файла (имя, EXIF) — тоже пользовательский ввод, который может использоваться в запросах/командах без должной санитизации C) Это относится только к Broken Access Control D) Загрузка файлов всегда безопасна
    Ответ: **B** (Имя файла, EXIF и другие метаданные — тоже пользовательский ввод; если их конкатенируют в SQL/команду, возникает инъекция. Загрузка файлов расширяет поверхность Injection.)

29. Command Injection payload вида "; whoami" эксплуатирует: A) отсутствие экранирования спецсимволов шелла при передаче ввода в системный вызов B) слабый TLS C) отсутствие CSRF-токена D) неправильную конфигурацию CORS
    Ответ: **A** (Payload «; whoami» использует разделители/метасимволы shell, когда ввод уходит в system call без безопасного API аргументов. Отсутствие экранирования позволяет добавить вторую команду.)

30. Инструмент sqlmap используется для: A) статического анализа кода B) автоматизированного обнаружения и эксплуатации SQL-инъекций C) сканирования Wi-Fi сетей D) анализа TLS-сертификатов
    Ответ: **B** (sqlmap автоматизирует обнаружение и эксплуатацию SQL Injection: fingerprint, payload’ы, извлечение данных. Это специализированный инструмент под SQLi, а не общий XSS-сканер.)

31. Что из перечисленного правильно описывает stacked queries (batch queries) в SQLi? A) Выполнение нескольких SQL-запросов подряд через один инъекционный ввод (разделённых ;), не всегда поддерживается всеми СУБД/драйверами B) Единственный тип SQL-инъекции C) Тип XSS D) Тип CSRF
    Ответ: **A** (Stacked/batch queries — выполнение нескольких SQL-операторов через один injection point (часто через «;»), но поддержка зависит от драйвера/СУБД. Не все стеки допускают такой режим.)

32. Почему WAF (Web Application Firewall) не должен рассматриваться как единственная защита от инъекций? A) WAF полностью устраняет риск сам по себе B) WAF — дополнительный слой (defense-in-depth), но может быть обойдён через обфускацию payload'ов; корневая защита — параметризация/валидация в коде C) WAF не влияет на инъекции вообще D) WAF заменяет необходимость патчинга
    Ответ: **B** (WAF — дополнительный слой и может обходиться обфускацией payload; корневая защита — параметризация, безопасные API и экранирование. WAF alone не заменяет исправление кода.)

33. Атака Blind XXE может использоваться для эксфильтрации данных через: A) DNS/HTTP out-of-band канал (внешний DTD, отправляющий данные на сервер атакующего) B) только через прямой вывод в отклик C) только через SMTP D) невозможна без прямого вывода
    Ответ: **A** (Blind XXE часто эксфильтрирует данные out-of-band через DNS/HTTP к внешнему DTD/серверу атакующего. Прямого содержимого entity в HTTP-ответе может не быть.)

34. Что из перечисленного — пример инъекции в контекст JavaScript-строки (отличается от инъекции в HTML-тег по способу экранирования)? A) <script>alert(1)</script> в теле страницы B) ввод, вставляемый внутрь var x = "USER_INPUT"; в inline-скрипте, требующий JS-escape, а не HTML-escape C) SQL UNION SELECT D) LDAP filter
    Ответ: **B** (Вставка в JS-строку (var x = "USER_INPUT";) требует JS-экранирования кавычек/спецсимволов, а не только HTML entity encoding. Неверный контекст экранирования оставляет XSS.)

35. Почему шаблонизаторы с «sandbox-режимом» (например, ограниченный Jinja2) снижают риск SSTI? A) Они полностью убирают возможность инъекции синтаксиса шаблона B) Они ограничивают доступные в шаблоне объекты/методы, снижая вероятность достижения RCE даже при инъекции в шаблон C) Sandbox не влияет на SSTI D) Требуется отключить шаблонизатор полностью
    Ответ: **B** (Sandbox/restricted mode шаблонизатора ограничивает доступные объекты и методы, затрудняя выход к RCE через SSTI. Это defense-in-depth наряду с запретом untrusted templates.)

36. Согласно данным OWASP 2025, категория Injection упала с #3 (2021) на #5 (2025) в рейтинге. Наиболее вероятная причина: A) инъекции больше не существуют B) улучшение индустриальных практик (широкое распространение ORM, параметризованных запросов, автоматических фреймворков экранирования) снизило частоту, хотя категория остаётся значимой C) OWASP решил исключить SQLi из списка D) Инъекции теперь относятся к A01
    Ответ: **B** (Injection опустилась с #3 (2021) до #5 (2025) во многом благодаря ORM, prepared statements и автоэкранированию фреймворков. Риск остаётся, но зрелость практик выросла.)

37. Что из перечисленного — правильный подход к экранированию вывода в атрибуте HTML-тега (например, <div title="USER_INPUT">)? A) HTML entity encoding для спецсимволов атрибута (", ', <, >, &) B) Достаточно только серверной валидации по regex C) Экранирование не требуется, если используется HTTPS D) Использование Base64
    Ответ: **A** (В HTML-атрибуте нужно HTML-entity encoding спецсимволов атрибута (« ' < > &), чтобы закрыть выход из значения. Иначе XSS возможен через разрыв атрибута.)

38. Fuzzing входных точек спецсимволами (' " ; -- <script> {{7*7}} $(whoami)) на пентесте применяется для: A) проверки производительности B) выявления потенциальных точек инъекции по аномальному поведению отклика (ошибки, задержки, отражение payload) C) проверки TLS D) проверки cookie-флагов
    Ответ: **B** (Фаззинг спецсимволами (' " ; -- <script> {{7*7}} и т.д.) помогает найти injection points по аномалиям: ошибкам, задержкам, отражению. Это разведка, а не готовая эксплуатация.)

39. Что из перечисленного справедливо про полиглот-payload'ы (polyglot payloads) в контексте тестирования на инъекции? A) Работают только для SQLi B) Специально сконструированы так, чтобы одновременно триггерить несколько типов инъекций (XSS+SQLi и т.д.) для эффективного первичного фаззинга C) Используются только для DoS D) Не имеют практического применения
    Ответ: **B** (Polyglot-payload’ы специально составлены, чтобы одновременно триггерить несколько типов инъекций (XSS+SQLi и др.) для ускорения тестирования. Это не «безопасный» ввод, а диагностический инструмент.)

40. Инъекция в HTTP-заголовок User-Agent, который затем логируется и отображается в админ-панели без экранирования, — пример: A) SSRF B) Stored XSS через нестандартную точку ввода C) CSRF D) LDAP Injection
    Ответ: **B** (User-Agent, попавший в логи и затем отрендеренный в HTML без экранирования, даёт Stored XSS через нестандартную точку ввода. Любой отражённый заголовок — потенциальный sink.)

41. Почему атрибут X-XSS-Protection считается устаревшим и его отсутствие сейчас не является проблемой согласно современным рекомендациям? A) Он никогда не работал B) Современные браузеры удалили встроенный XSS-auditor из-за собственных уязвимостей; актуальная защита — CSP C) Он всё ещё обязателен и является главной защитой D) Он относится к SQLi, а не XSS
    Ответ: **B** (X-XSS-Protection устарел: современные браузеры убрали XSS-auditor из-за его собственных проблем. Актуальные меры — CSP, контекстное экранирование и безопасные фреймворки.)

42. Инъекция через десериализацию (например, Java gadget chains) пересекается с какой ещё категорией OWASP? A) A02 Misconfiguration B) A08 Software/Data Integrity Failures (небезопасная десериализация) C) A07 Authentication Failures D) A09 Logging Failures
    Ответ: **B** (Небезопасная десериализация (gadget chains) пересекается с A08 Software/Data Integrity Failures, хотя payload тоже «инъецирует» поведение. В Top 10:2025 это в первую очередь integrity/deserial class.)

43. Что из перечисленного — верное описание «второго порядка» (stored) command injection? A) Команда выполняется сразу при вводе B) Вредоносный ввод сохраняется (например, в конфигурации/БД) и позже используется в системном вызове другим компонентом/процессом C) Не существует такого типа D) Работает только с SQL
    Ответ: **B** (Second-order command injection: вредоносный ввод сохраняется (конфиг/БД), а позже другой компонент подставляет его в system call. Эксплуатация отложена и может быть в другом сервисе.)

44. GraphQL-инъекции (например, через nested queries для DoS или injection в resolver) относятся к: A) отдельной категории вне OWASP B) подмножеству Injection (A05) с учётом специфики GraphQL как альтернативы REST C) исключительно к SSRF D) исключительно к CSRF
    Ответ: **B** (Инъекции и abuse GraphQL (resolver injection, nested query DoS) относятся к подмножеству Injection (A05) с учётом специфики GraphQL. Это не отдельная категория Top 10.)

45. Почему санитизация markdown/rich-text контента (например, в комментариях блога) — частый источник Stored XSS? A) Markdown безопасен по умолчанию всегда B) Неправильная конфигурация markdown-парсера может пропускать HTML/JS-теги в итоговый рендер, обходя базовую защиту C) Markdown никогда не рендерится в HTML D) Не относится к XSS
    Ответ: **B** (Некорректная настройка markdown/rich-text парсера может пропустить HTML/JS в итоговый рендер, обходя ожидание «только текст». Санитизация rich content — частый источник Stored XSS.)

46. Инъекция в regex (ReDoS — Regular Expression Denial of Service) относится к подклассу: A) SQL Injection B) Injection-класса уязвимостей, приводящих к DoS через катастрофический backtracking в неоптимальном regex-паттерне C) XSS D) CSRF
    Ответ: **B** (ReDoS — инъекция/злоупотребление регулярными выражениями через catastrophic backtracking, ведущее к DoS. Это injection-class проблема производительности/доступности, а не кража данных.)

47. Что из перечисленного — правильная защита от Command Injection, если экранирование ввода технически сложно реализовать надёжно? A) Использование allow-list разрешённых команд/аргументов и API языка программирования вместо вызова shell (например, subprocess с list аргументов вместо shell=True) B) Просто увеличить логирование C) Использовать более длинные пароли D) Отключить HTTPS
    Ответ: **A** (Против Command Injection предпочтительны allow-list команд/аргументов и API без shell (exec с массивом аргументов), а не фильтрация «опасных» символов. Так control plane не строится из строк пользователя.)

48. Почему тестирование инъекций через файлы cookie/заголовки важно, а не только через параметры формы/URL? A) Cookie и заголовки никогда не обрабатываются сервером B) Любая точка, откуда сервер читает пользовательский ввод (включая cookie, заголовки, JSON body), потенциально уязвима, если используется в запросе/команде без валидации C) Заголовки нельзя подделать D) Cookie автоматически экранируются браузером
    Ответ: **B** (Cookies, заголовки и JSON body — такие же untrusted inputs, как поля формы. Если сервер использует их в запросах/выводе без защиты, инъекция возможна и там.)

49. AST-based/семантический анализ кода превосходит простой regex-based поиск инъекций тем, что: A) он медленнее и потому хуже B) он понимает структуру кода (поток данных от source к sink), а не просто ищет текстовые паттерны, снижая число false positive/negative C) он не может анализировать SQL D) он работает только на скомпилированном коде
    Ответ: **B** (AST/семантический анализ отслеживает поток данных от source к sink, а не только текстовые regex-паттерны. Это снижает ложные срабатывания и находит нетривиальные пути инъекции.)

50. Какая мера НАИБОЛЕЕ эффективна как единая root-cause защита против большинства подтипов Injection одновременно? A) Использование WAF как единственной меры B) Строгое разделение data plane и control plane на уровне API языка (параметризация/безопасные API) + контекстное экранирование вывода + позитивная валидация ввода C) Увеличение логирования запросов D) Отключение JavaScript на клиенте
    Ответ: **B** (Самая эффективная корневая защита — строгое разделение data plane и control plane через параметризацию и безопасные API языка. Валидация и WAF дополняют, но не заменяют это разделение.)

## A06:2025 — Insecure Design (50 вопросов)

1. В чём ключевое отличие Insecure Design от Security Misconfiguration? A) Это одно и то же B) Insecure Design — отсутствие нужного контроля в самой архитектуре, даже при идеальной реализации; Misconfiguration — плохая настройка правильно спроектированного контроля C) Insecure Design относится только к паролям D) Misconfiguration нельзя исправить патчем
   Ответ: **B** (Insecure Design — отсутствие нужного контроля в архитектуре даже при идеальной реализации; Misconfiguration — неверная настройка уже заложенного контроля. Это разные root cause: «не спроектировали» vs «настроили плохо».)

2. Почему Insecure Design «нельзя исправить простым патчем»? A) Патчи вообще не выпускаются для веб-приложений B) Проблема заложена на уровне архитектуры/дизайна, и требует пересмотра модели, а не точечного изменения кода C) Патчи слишком дорогие D) Всегда можно исправить одним патчем
   Ответ: **B** (Insecure Design нельзя «залатать» одной строкой: отсутствует или неверна сама модель/процесс, нужен пересмотр архитектуры и требований. Точечный патч не добавляет контроль, которого нет в дизайне.)

3. Threat modeling должен выполняться: A) после релиза, если найдены уязвимости B) на этапе проектирования (design phase), до написания кода C) только при аудите раз в год D) не требуется для веб-приложений
   Ответ: **B** (Threat modeling выполняют на этапе проектирования, до кода, чтобы заложить угрозы и контроли в архитектуру. После релиза остаётся лишь дорогое «затыкание» уже встроенных пробелов.)

4. Пример business logic abuse: A) SQL-инъекция в форме поиска B) Использование легитимного функционала возврата средств много раз подряд для получения средств сверх уплаченных (endless refund loop) C) Утечка памяти в парсере D) Слабый TLS cipher
   Ответ: **B** (Endless refund loop — abuse легитимного бизнес-сценария возврата без архитектурных лимитов/идемпотентности. Это business logic abuse, а не классическая SQLi или слабый TLS.)

5. STRIDE — это: A) фреймворк threat modeling (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege) B) алгоритм шифрования C) СУБД D) инструмент сканирования портов
   Ответ: **A** (STRIDE — фреймворк threat modeling: Spoofing, Tampering, Repudiation, Information disclosure, DoS, Elevation of privilege. Он структурирует анализ угроз, а не является алгоритмом шифрования.)

6. Race condition в бизнес-логике (например, параллельные запросы на списание средств) относится к: A) Cryptographic Failure B) Insecure Design — если архитектура не предусматривает атомарность/блокировку критичных операций C) Security Misconfiguration D) XSS
   Ответ: **B** (Race condition в бизнес-логике (параллельные списания) — Insecure Design, если архитектура не обеспечивает атомарность и блокировки. Без design-level синхронизации код «работает», но злоупотребим.)

7. Почему отсутствие лимита на количество применений промокода — пример Insecure Design, а не бага реализации? A) Промокод — не связан с дизайном B) Дизайн бизнес-процесса изначально не предусмотрел ограничение как требование, поэтому даже безошибочная реализация «как задумано» остаётся уязвимой C) Это всегда Cryptographic Failure D) Это относится только к Injection
   Ответ: **B** (Отсутствие лимита на применение промокода — пробел требований/дизайна процесса: реализация «как задумано» остаётся exploitable. Это не баг строки кода, а missing business rule.)

8. Reference architecture и secure design patterns, переиспользуемые между проектами, помогают предотвратить Insecure Design, потому что: A) ускоряют компиляцию B) закладывают проверенные защитные механизмы (аутентификация, rate limiting) на уровне архитектуры с самого начала, а не постфактум C) не имеют отношения к безопасности D) заменяют необходимость тестирования

9. Attack tree в threat modeling используется для: A) визуализации возможных путей атаки на систему от цели атакующего до конкретных техник B) хранения паролей C) шифрования данных D) построения ER-диаграммы БД

11. PASTA (Process for Attack Simulation and Threat Analysis) — это: A) язык программирования B) методология threat modeling, ориентированная на бизнес-риски C) алгоритм хеширования D) сетевой протокол
    Ответ: **B** (PASTA — методология threat modeling, ориентированная на бизнес-риск и симуляцию атак. Это процесс анализа, а не язык программирования или сканер портов.)

12. Что из перечисленного — пример abuse-case тестирования (в противовес use-case)? A) Заплатки всегда работают лучше B) Архитектурно встроенный rate limiting предусматривает лимиты на уровне пользователя/API/транзакции системно, а не точечно для одного обнаруженного случая злоупотребления C) Rate limiting не связан с design D) Rate limiting нужен только для DDoS

    Ответ: **B** (В SDL threat modeling делают для критичных user stories/фич на этапе дизайна, до написания кода. Поздний анализ перед релизом уже не закладывает контроли в модель.)

A) Утечка памяти в конкретной функции из-за забытого free() B) Архитектура API вообще не предусматривает ограничение размера/сложности запроса (например, произвольно глубокий вложенный JSON/GraphQL query), допуская DoS через дизайн API C) Ошибка в SQL-запросе D) Слабый пароль администратора
    Ответ: **B** (API без лимитов размера/сложности запросов (неограниченная вложенность JSON/GraphQL) — insufficient design resource limits. Это открывает DoS/resource exhaustion на уровне приложения.)

23. Согласно принципам secure design, критичные защитные компоненты (аутентификация, rate limiting) должны быть реализованы: A) заново в каждом модуле для гибкости B) как переиспользуемые сервисы/библиотеки, применяемые единообразно во всём приложении C) только во фронтенде D) отдельно для каждого разработчика по своему усмотрению
    Ответ: **B** (Критичные контроли (auth, rate limit) должны быть переиспользуемыми сервисами/библиотеками, единообразно применяемыми во всём приложении. Иначе «прокладки» в каждом модуле дают пробелы дизайна.)

24. Attack surface analysis на этапе дизайна помогает: A) увеличить производительность B) заранее определить все точки взаимодействия системы с недоверенными источниками и спроектировать для них соответствующие защитные меры C) заменить необходимость тестирования D) не имеет практического применения
    Ответ: **B** (Attack surface analysis на design stage выявляет все точки взаимодействия с untrusted источниками и заранее проектирует контроли. Это проактивно, а не постфактум после инцидента.)

25. Что из перечисленного — правильный пример защиты от race condition в бизнес-логике на уровне дизайна? A) Использование database-level lock/atomic transaction при критичных многошаговых операциях (например, списание баланса) B) Просто увеличение таймаута запроса C) Отключение логирования D) Использование более длинного пароля
    Ответ: **A** (Защита от race condition: DB-lock или атомарная транзакция на критичных многошаговых операциях (списание баланса). Без этого параллельные запросы обходят бизнес-инварианты.)

26. Concept of «Trust but verify» относится к Insecure Design тем, что: A) означает полное отсутствие проверок для «доверенных» источников B) современный принцип secure design предполагает проверку даже внутренних/доверенных источников (аналог Zero Trust), а не слепое доверие C) относится только к внешним API D) не связано с дизайном системы
    Ответ: **B** («Trust but verify» / Zero Trust: даже «внутренние» источники нужно проверять — secure design не опирается на слепое доверие. Иначе компромисс одного компонента открывает всё.)

27. Что из перечисленного — пример Insecure Design в контексте пароля/аутентификации, отличный от Authentication Failure (A07)? A) Слабый пароль пользователя (A07) B) Архитектура вообще не предусматривает возможность внедрения MFA в будущем без полного редизайна системы аутентификации (архитектурное ограничение) C) Отсутствие rate limiting на login (A07) D) Использование MD5 для хеша пароля (A04)
    Ответ: **B** (Архитектура auth, в которую нельзя добавить MFA без полной переделки, — Insecure Design (плохая расширяемость безопасности). Это не про слабый пароль сам по себе, а про модель системы.)

28. Почему сценарии abuse-case важно продумывать вместе с продуктовой командой, а не только security-командой? A) Продуктовая команда не имеет отношения к безопасности B) Понимание бизнес-логики и намерений пользователей у продуктовой команды помогает выявить, какие легитимные функции можно злоупотребить не по назначению C) Security-команда всегда справляется без продукта D) Это требуется только для стартапов
    Ответ: **B** (Product owner знает бизнес-правила и intent пользователей, поэтому совместно с ним легче найти abuse-cases легитимных фич. Без бизнеса threat model пропускает логические дыры.)

29. Что из перечисленного иллюстрирует разницу между «vulnerability» и «missing control» применительно к Insecure Design? A) Это одно и то же понятие B) Vulnerability — конкретный баг в реализации существующего контроля; missing control — контроль, который должен был существовать по замыслу дизайна, но отсутствует полностью C) Missing control относится только к сети D) Vulnerability относится только к паролям
    Ответ: **B** (Vulnerability — дефект реализации уже существующего контроля; missing control — контроль вообще не заложен в дизайн. Insecure Design как раз про второе.)

30. Согласно OWASP, для эффективного secure design важно моделировать угрозы для: A) только внешних пользователей B) всех сущностей, взаимодействующих с системой — включая внутренних пользователей, партнёров, автоматизированные системы/боты C) только администраторов D) только мобильных клиентов
    Ответ: **B** (По OWASP нужно моделировать угрозы для всех сущностей, взаимодействующих с системой: пользователей, партнёров, автоматизации, внутренних ролей. Ограничение только «внешним хакером» оставляет слепые зоны.)

31. Пример недостаточно продуманного лимита при регистрации (например, отсутствие проверки на массовую автоматическую регистрацию аккаунтов ботами для накрутки реферальной программы) относится к: A) SQL Injection B) Insecure Design / business logic abuse C) Cryptographic Failure D) Security Logging Failure
    Ответ: **B** (Регистрация без лимитов/проверок (массовые аккаунты) — Insecure Design и business logic abuse. Легитимная функция становится инструментом накрутки и fraud.)

32. Что из перечисленного — верная практика реагирования на найденный на пентесте Insecure Design баг (в отличие от классической уязвимости кода)? A) Просто исправить один эндпоинт локальным патчем и закрыть тикет B) Эскалировать архитектурной/продуктовой команде для пересмотра дизайна процесса, так как локальный патч может не покрыть все варианты обхода C) Игнорировать, если PoC не сработал с первой попытки D) Понизить severity автоматически, так как это не «классическая» уязвимость
    Ответ: **B** (Находка Insecure Design на пентесте требует эскалации к architecture/product для пересмотра процесса; локальный патч может не закрыть модель. Нужен redesign, а не только hotfix строки.)

33. Zero-day «design flaw» отличается от zero-day «implementation bug» тем, что: A) design flaw невозможно эксплуатировать B) design flaw требует пересмотра архитектуры для устранения, а не просто патча кода, и часто затрагивает несколько компонентов системы одновременно C) implementation bug никогда не патчится D) Это синонимы
    Ответ: **B** (Design-flaw zero-day требует изменения архитектуры, а implementation bug — точечного патча кода. Design flaws обычно шире по impact и дольше закрываются.)

34. Какая из следующих мер относится к «Secure design patterns and paved road», рекомендуемым OWASP? A) Каждая команда изобретает собственную реализацию аутентификации с нуля B) Централизованные, проверенные библиотеки/сервисы (auth-as-a-service, rate-limiting middleware), обязательные к использованию всеми командами C) Отсутствие стандартов между командами D) Отказ от code review
    Ответ: **B** (Paved road — централизованные проверенные сервисы (auth-as-a-service, rate-limit middleware), обязательные для команд. Это secure design patterns, снижающие ad-hoc дыры.)

35. Что из перечисленного — правильный пример защиты от «scalping»/накрутки лимитированных товаров через дизайн (не через патч после инцидента)? A) Просто добавить CAPTCHA постфактум после того, как весь товар уже скуплен ботами один раз B) Изначально заложить в архитектуру покупки: rate limiting на аккаунт/IP, поведенческий анализ, лимит количества товара на аккаунт как часть бизнес-требований C) Игнорировать проблему D) Увеличить цену товара вдвое
    Ответ: **B** (Против scalping: rate limiting покупок per account/IP, behavioral analysis и лимиты количества на аккаунт, заложенные в flow. Только «честные пользователи» в UI не останавливают ботов.)

36. Почему «единая точка отказа» (single point of failure) для security-контроля — пример плохого дизайна? A) Это не относится к безопасности B) Если весь security полагается на один непроверяемый механизм без резервных/дополняющих слоёв защиты (defense-in-depth), компрометация этого единственного механизма ведёт к полному провалу защиты C) SPOF — это только про доступность (availability), не про security D) SPOF невозможен в современных системах
    Ответ: **B** (Single point of failure security control: вся защита на одном непроверяемом механизме без defense-in-depth. Падение/обход одной точки обнуляет безопасность — плохой дизайн.)

37. Что из перечисленного — пример правильного «fail securely» дизайна платежной системы (пересекается с A10, но закладывается на этапе A06)? A) При сбое проверки лимита транзакции — по умолчанию разрешить транзакцию (fail open) B) При сбое проверки лимита транзакции — по умолчанию отклонить транзакцию и залогировать инцидент (fail closed) C) Игнорировать сбои проверки D) Повторить транзакцию автоматически без логирования
    Ответ: **B** (Fail securely: при сбое проверки лимита транзакции — deny by default и лог (fail closed), а не «пропустить». Иначе отказ контроля становится открытой дверью.)

38. Согласно OWASP, недостаточность threat modeling чаще всего проявляется в: A) отсутствии тестирования производительности B) неучтённых на этапе дизайна сценариях злоупотребления/атаки, которые обнаруживаются только постфактум через инцидент или пентест C) устаревшей документации API D) отсутствии CI/CD
    Ответ: **B** (Недостаточный threat modeling чаще проявляется как неучтённые abuse/attack-сценарии, обнаруженные только инцидентом или пентестом. Пробел на design stage догоняет позже.)

39. Пример business logic flaw в e-commerce: возможность применить один и тот же промокод «первая покупка -50%» многократно на разные заказы того же пользователя из-за отсутствия проверки истории использования. Это относится к: A) SQL Injection B) Insecure Design (недостаточность бизнес-правил в архитектуре) C) XSS D) SSRF
    Ответ: **B** (Повторное применение «first-order» скидки — Insecure Design: business rules не enforce’ятся архитектурой. Нужны идемпотентность, учёт использования и серверные ограничения.)

40. Что из перечисленного — правильный подход к тестированию race condition на пентесте? A) Отправка запросов строго последовательно с задержкой B) Одновременная (параллельная) отправка идентичных запросов через инструменты типа Burp Turbo Intruder/специализированные скрипты для минимизации сетевой задержки между запросами C) Проверка только через UI вручную одним запросом D) Проверка версии TLS
    Ответ: **B** (Гонки тестируют параллельной отправкой одинаковых запросов (Turbo Intruder и аналоги) и проверкой инвариантов (баланс, остатки). Последовательный ручной клик race не воспроизводит.)

41. Почему «design review» должен быть отдельным этапом от «code review» в SDLC? A) Это одно и то же, разделение не нужно B) Code review проверяет корректность реализации существующего дизайна, design review — адекватность самого дизайна архитектурным угрозам до написания кода C) Design review не требуется для веб-приложений D) Design review проводится только после релиза
    Ответ: **B** (Design review проверяет адекватность модели и наличие контролей; code review — корректность реализации уже выбранного дизайна. Это разные стадии SDLC с разными вопросами.)

42. Что из перечисленного — пример недостаточного дизайна процесса восстановления пароля, ведущего к account takeover? A) Использование bcrypt для хранения пароля B) Процесс восстановления полагается только на секретный вопрос с легко угадываемым/публично известным ответом (например, «девичья фамилия матери»), заложенный в архитектуру без альтернативы C) Использование HTTPS для формы восстановления D) Rate limiting на форме логина
    Ответ: **B** (Сброс пароля только через легко угадываемый secret question — плохой дизайн recovery-процесса. Нужны криптостойкие токены, MFA-каналы и сроки жизни, а не публичные «ответы».)

43. Согласно принципам Insecure Design, «избыточное доверие к клиентской стороне» (client-side trust) проявляется, когда: A) сервер полностью валидирует все данные независимо от клиента B) бизнес-логика (например, расчёт цены товара) частично или полностью выполняется/проверяется на клиенте, и сервер принимает итоговое значение от клиента без пересчёта C) клиент не имеет доступа к API D) используется HTTPS
    Ответ: **B** (Excessive client-side trust: бизнес-логика (цена, скидки) считается/доверяется на клиенте без серверной валидации. Клиент атакующий контролирует, сервер должен enforce’ить правила.)

44. Что из перечисленного — пример правильной архитектуры multi-tenant SaaS с точки зрения secure design?     Ответ: **B** (Secure multi-tenant: изоляция данных в архитектуре (отдельные schema / обязательный enforceable tenant_id). «Надеемся, что разработчик не забудет WHERE» — не дизайн.)

45. Почему «недостаточно продуманный» workflow одобрения (approval workflow) — например, отсутствие проверки, что одобряющий не является тем же лицом, что запрашивающий (segregation of duties) — относится к Insecure Design? A) Это относится только к HR-процессам, не к ИБ B) Отсутствие архитектурного разделения ролей запрашивающего/одобряющего позволяет одному скомпрометированному или недобросовестному аккаунту одобрить собственный запрос (например, повышение прав, крупный перевод) C) Это невозможно предотвратить архитектурно D) Не относится к веб-приложениям
    Ответ: **B** (Workflow без разделения requester/approver даёт одному скомпрометированному аккаунту полный цикл согласования. Архитектурное SoD (segregation of duties) — обязательный design control.)

46. Что из перечисленного лучше всего описывает подход «secure by default» в контексте Insecure Design? A) Все настройки безопасности отключены по умолчанию для удобства пользователя B) Система по умолчанию сконфигурирована максимально безопасно, и пользователь должен осознанно ослабить защиту, если это необходимо, а не наоборот C) Secure by default относится только к паролям D) Не имеет отношения к дизайну
    Ответ: **B** (Secure by default: система изначально максимально безопасна, а ослабление — сознательное действие пользователя/админа. Это design/product principle, снижающий accidental exposure.)

47. Пример архитектурного просчёта: система бронирования не предусматривает лимит на количество одновременных «удержаний» (holds) мест одним пользователем, что позволяет заблокировать весь инвентарь без реальной покупки.     Ответ: **B** (Букинг без лимита «зависших» резервов — Insecure Design / resource exhaustion через бизнес-логику: можно заблокировать весь inventory. Нужны TTL холдов и лимиты на аккаунт.)

48. Согласно рекомендациям OWASP по Insecure Design, «limit resource consumption by user or service» должно применяться на уровне: A) только сетевого firewall B) архитектуры приложения и API — транзакций, запросов, пользовательских действий, а не только на уровне инфраструктуры C) только базы данных D) только фронтенда
    Ответ: **B** (Лимиты потребления ресурсов по OWASP — на уровне app/API: транзакции, запросы, действия пользователя, а не только infra quotas. Иначе abuse бизнес-операций остаётся открытым.)

49. Почему «доверие к третьей стороне без верификации» (например, автоматическое принятие вебхука от партнёра без проверки подписи) относится к Insecure Design? A) Вебхуки всегда безопасны B) Если архитектура изначально не предусматривает верификацию источника/подписи входящих вебхуков, любой, кто узнает URL, может подделать событие C) Не относится к дизайну, это Injection D) Вебхуки не используются в enterprise-системах
    Ответ: **B** (Доверие к third-party webhook без проверки подписи/источника — Insecure Design: любой, кто знает URL, может слать события. Архитектура должна закладывать верификацию входов.)

50. Какая мера НАИБОЛЕЕ комплексно снижает риск категории Insecure Design в организации в целом? A) Только регулярное сканирование уязвимостей после релиза B) Интеграция threat modeling и security requirements в самый ранний этап SDLC (до написания кода) как обязательный процесс для критичных фич, плюс переиспользуемые secure-паттерны C) Использование только антивируса на серверах D) Увеличение частоты релизов без изменения процесса
    Ответ: **B** (Наиболее комплексно риск Insecure Design снижает встраивание threat modeling и security requirements в самый ранний SDLC — до кода. Поздние патчи не заменяют secure-by-design.)

A) Java медленнее других языков B) Обилие широко распространённых библиотек в classpath enterprise-приложений увеличивает вероятность найти пригодную для gadget chain комбинацию классов C) Java не поддерживает сериализацию D) Enterprise-приложения никогда не используют сериализацию
    Ответ: **B** (В enterprise Java classpath полно библиотек, из которых легче собрать рабочую gadget chain для десериализации.)

25. Что из перечисленного — правильная тестовая методология поиска insecure deserialization на пентесте? A) Только фаззинг форм ввода текстом B) Идентификация точек, принимающих сериализованные данные (по формату — Java magic bytes, PHP O:, Python pickle opcode), затем тестирование через инструменты типа ysoserial/phpggc с последующим мониторингом на выполнение кода (например, через OOB DNS callback) C) Проверка только заголовков ответа D) Проверка TLS-сертификата
    Ответ: **B** (На пентесте ищут эндпоинты с сериализованными данными (magic bytes, PHP O:, pickle), гоняют ysoserial/phpggc и ловят RCE через OOB (DNS).)

26. Почему организациям стоит избегать десериализации объектов из данных, полученных напрямую от клиента, даже если клиент — «доверенное» мобильное приложение той же организации? A) Мобильные приложения не могут быть скомпрометированы B) Клиентское приложение может быть декомпилировано/модифицировано атакующим (например, через reverse engineering + перехват трафика), поэтому клиент — недоверенный источник по умолчанию C) Мобильные приложения не поддерживают сериализацию D) Не является риском
    Ответ: **B** (Клиентское приложение можно reverse-engineer’ить и подменить трафик, поэтому данные «от своего мобильного приложения» всё равно недоверенные.)

27. Что из перечисленного — верное про JSON как формат обмена данными в контексте A08? A) JSON изначально исполняемый формат, как pickle B) JSON сам по себе не содержит исполняемого кода (в отличие от объектной сериализации), что снижает (но не устраняет полностью, при неправильном парсинге) риск integrity failure при его использовании вместо бинарной сериализации C) JSON всегда небезопасен D) JSON не может использоваться для передачи структурированных данных
    Ответ: **B** (JSON сам по себе не исполняет код, в отличие от object-сериализации, и снижает (но не обнуляет при плохом парсере) риск integrity failure.)

28. Manifest confusion/dependency confusion атака (внутренний пакет с тем же именем, что публичный, но публичный имеет более высокую версию) относится к пересечению: A) A08 и A03 — компрометация целостности источника зависимости C) исключительно XSS D) исключительно CSRF
    Ответ: **A** (Dependency/manifest confusion компрометирует источник зависимости: это пересечение supply chain (A03) и integrity артефакта (A08).)

29. Почему верификация цифровой подписи должна выполняться ДО распаковки/использования содержимого архива/пакета, а не после? A) Порядок не имеет значения B) Обработка непроверенного содержимого до верификации подписи может само по себе привести к эксплуатации уязвимости парсера, даже если сама подпись впоследствии окажется неверной C) Верификация после быстрее D) Требуется только для ZIP-архивов
    Ответ: **B** (Подпись нужно проверять до распаковки: иначе уже парсинг вредоносного архива может эксплуатировать уязвимость, даже если подпись потом «не сойдётся».)

30. Что из перечисленного — пример «software integrity failure» в мобильном приложении? A) Слабый пароль пользователя B) Приложение не проверяет целостность собственного кода/ресурсов при запуске, позволяя выполнение модифицированной (patched) версии с обходом security-проверок C) Отсутствие MFA D) Использование HTTP вместо HTTPS
    Ответ: **B** (Mobile integrity failure — отсутствие проверки целостности своего кода/ресурсов, из-за чего запускается patched-сборка с обходом security-проверок.)

31. Почему объектная десериализация опаснее, чем парсинг структурированного текстового формата с явной схемой (например, Protocol Buffers с строгой схемой)? A) Между ними нет разницы в безопасности B) Объектная десериализация напрямую инстанцирует произвольные классы, обнаруженные в потоке данных, тогда как формат со строгой схемой ограничивает набор допустимых полей/типов заранее C) Protocol Buffers всегда медленнее D) Объектная сериализация быстрее, поэтому безопаснее
    Ответ: **B** (Object-десериализация инстанцирует произвольные классы из потока; schema-форматы (Protobuf и т.п.) заранее ограничивают поля и типы.)

32. Что из перечисленного описывает атаку «type confusion» через полиморфную десериализацию (например, Jackson с enableDefaultTyping)? A) Атакующий указывает произвольный класс для инстанцирования через поле типа в JSON, если библиотека сконфигурирована принимать тип из самих данных, а не из строгой схемы B) Не является риском при использовании JSON C) Относится только к XML D) Требует физического доступа
    Ответ: **A** (Type confusion через polymorphic typing (Jackson enableDefaultTyping): тип берётся из данных, и атакующий подставляет произвольный класс.)

33. Почему «trust but don't verify» — антипаттерн, релевантный категории A08? A) Это рекомендуемая практика B) Слепое доверие к источнику данных/кода без криптографической верификации целостности — суть корневой причины Integrity Failures C) Не относится к A08 D) Verify всегда избыточен при использовании HTTPS
    Ответ: **B** («Trust but don’t verify» — корневая причина Integrity Failures: доверие к источнику без криптографической проверки целостности.)

34. Что из перечисленного — верно про npm postinstall-скрипты в контексте integrity? A) Postinstall-скрипты не могут исполнять произвольный код B) Postinstall-скрипты автоматически исполняются при установке пакета и могут содержать вредоносный код, если пакет/его зависимость скомпрометированы (пересечение с A03) C) Postinstall-скрипты требуют ручного подтверждения всегда по умолчанию D) Не относится ни к A03, ни к A08
    Ответ: **B** (npm postinstall выполняется автоматически при install и может запустить malware, если пакет скомпрометирован (пересечение с A03).)

35. Почему хранение хешей эталонных версий файлов (integrity monitoring / FIM — File Integrity Monitoring) полезно для обнаружения нарушения целостности production-системы? A) FIM замедляет систему без пользы B) Позволяет обнаружить несанкционированное изменение критичных файлов/бинарников постфактум, сравнивая текущий хеш с эталонным C) FIM заменяет необходимость подписи артефактов D) FIM относится только к сетевому трафику
    Ответ: **B** (FIM сравнивает текущие хеши критичных файлов с эталоном и обнаруживает несанкционированные изменения в production.)

36. Что из перечисленного — пример правильной защиты пайплайна релиза от «time-of-check to time-of-use» (TOCTOU) race condition при верификации подписи? A) Проверка подписи артефакта задолго до его фактического использования/деплоя, с возможностью подмены файла между проверкой и использованием B) Проверка подписи непосредственно перед использованием артефакта, с последующим немедленным использованием того же самого проверенного объекта без промежуточной подмены C) TOCTOU не относится к integrity D) Не требует внимания
    Ответ: **B** (Против TOCTOU подпись проверяют непосредственно перед использованием того же объекта, без окна для подмены между check и use.)

37. Согласно принципам A08, зависимости и файлы должны приходить: A) из любого удобного источника для скорости разработки B) из ожидаемых, доверенных репозиториев через verified/signed channel C) исключительно с локального диска разработчика D) без проверки происхождения, если используется VPN
    Ответ: **B** (По A08 зависимости и файлы должны приходить из ожидаемых доверенных репозиториев по verified/signed каналу.)

38. Что из перечисленного описывает риск конкретно для десериализации через YAML (например, PyYAML yaml.load() без safe_load)? A) YAML не поддерживает объекты B) Небезопасная загрузка YAML может позволить инстанцирование произвольных Python-объектов из тегов вида !!python/object, аналогично pickle C) YAML всегда безопасен D) YAML относится только к конфигурационным файлам, не к данным пользователя
    Ответ: **B** (Небезопасный yaml.load() (без safe_load) может инстанцировать произвольные Python-объекты через теги !!python/object, аналогично pickle.)

39. Почему auto-update механизм плагина браузера/расширения — частая цель атак на целостность? A) Расширения не имеют доступа к данным пользователя B) Скомпрометированный канал обновления расширения позволяет незаметно для пользователя доставить вредоносный код с широким доступом к браузерным данным, минуя app store review при последующих «тихих» обновлениях C) Расширения обновляются вручную всегда D) Расширения не относятся к A08
    Ответ: **B** (Скомпрометированный auto-update расширения доставляет malware «тихо», с широким доступом к браузеру и в обход app-store review на последующих обновлениях.)

40. Что из перечисленного — верное про связь между Log4Shell (Log4j RCE) и категорией A08 vs A03? A) Log4Shell — исключительно проблема integrity, не supply chain B) Log4Shell — пример уязвимого компонента (A03, известная CVE в зависимости), при этом сама техника эксплуатации через JNDI lookup демонстрирует более широкую проблему небезопасной десериализации/интерпретации недоверенных данных (пересечение с A05/A08) C) Log4Shell не связан ни с одной из категорий D) Log4Shell относится только к A01
    Ответ: **B** (Log4Shell — уязвимый компонент (A03), а техника через JNDI/интерпретацию недоверенных данных пересекается с injection/integrity (A05/A08).)

41. Почему «code signing certificate», используемый для подписи ПО, сам требует строгой защиты (в HSM, с ограниченным доступом)? A) Не имеет значения, где хранится B) Компрометация приватного ключа подписи позволяет атакующему подписать вредоносный код как легитимный, полностью обходя механизм верификации целостности C) Сертификаты подписи невозможно украсть D) Требуется только для open-source ПО
    Ответ: **B** (Утечка private code-signing key позволяет подписать malware как легитимное ПО и полностью обойти проверку подписи.)

42. Что из перечисленного — риск «CI/CD platform trust boundary violation»? A) CI-раннер, используемый для сборки нескольких проектов разных команд без изоляции, позволяет потенциально скомпрометированной сборке одного проекта повлиять на артефакты другого через общее состояние раннера B) Не является риском при использовании облачного CI C) Относится только к self-hosted раннерам D) Не связано с integrity
    Ответ: **A** (Общий CI-runner без изоляции между командами — нарушение trust boundary: одна скомпрометированная сборка может отравить артефакты другой.)

43. Почему верификация checksum (например, SHA-256) файла, скачанного с открытого зеркала, недостаточна сама по себе для полной гарантии целостности (в отличие от криптографической подписи)? A) Checksum и подпись эквивалентны по гарантии B) Checksum без подписи можно пересчитать и опубликовать заново для подменённого файла тем же злоумышленником, который скомпрометировал источник — подпись требует обладания приватным ключом издателя, которого у атакующего нет C) Checksum всегда надёжнее подписи D) Checksum не имеет отношения к integrity
    Ответ: **B** (Один checksum без подписи атакующий может пересчитать для подменённого файла; подпись требует приватного ключа издателя.)

    Ответ: **A** (Небезопасный trigger вроде pull_request_target с секретами даёт внешнему PR выполнение кода и доступ к secrets, нарушая integrity пайплайна.)

Согласно рекомендациям A08, безопаснее ли использовать формат данных с явной, ограниченной схемой (JSON Schema, Protobuf) вместо языко-специфичной бинарной сериализации для межсервисного взаимодействия? A) Нет разницы B) Да — схема ограничивает набор допустимых полей/типов, снижая поверхность атаки по сравнению с произвольной инстанциацией объектов C) Бинарная сериализация всегда безопаснее D) Формат не имеет значения для integrity
    Ответ: **B** (Форматы со схемой (JSON Schema, Protobuf) ограничивают типы и поля и безопаснее языко-специфичной бинарной сериализации между сервисами.)

46. Что из перечисленного — правильная мера при обнаружении, что production использует .NET BinaryFormatter для десериализации данных, полученных от внешнего клиента? A) Оставить как есть, если инцидентов пока не было B) Приоритетно мигрировать на безопасную альтернативу (например, System.Text.Json с строгой схемой) и/или изолировать процесс десериализации C) Увеличить логирование без изменения кода D) Отключить только логирование ошибок

47. Почему «pull-based» обновление конфигурации (агент сам запрашивает и верифицирует подпись новой конфигурации с сервера) считается более безопасным паттерном, чем «push-based» без верификации?     Ответ: **B** (Pull-update с проверкой подписи на агенте позволяет отклонить неподписанную конфигурацию; «голый» push опирается только на защиту канала.)

48. Что из перечисленного — пример нарушения целостности данных (Data Integrity Failure, не Software) в контексте A08?     Ответ: **B** (Data Integrity Failure — отсутствие подписи/checksum критичных бизнес-данных (например транзакций) между сервисами, что позволяет незаметную подмену «в полёте».)

A) Не имеет значения для integrity B) Позволяет расследовать инциденты нарушения целостности пайплайна постфактум и обнаружить несанкционированные изменения, что также пересекается с A09 (Logging) C) Требуется только для соответствия ISO D) Замедляет работу CI без пользы
    Ответ: **B** (Аудит изменений CI/CD (кто/когда/что) помогает расследовать integrity-инциденты и пересекается с A09 Logging.)

A) Только антивирус на серверах B) Обязательная криптографическая подпись всех артефактов/обновлений + верификация подписи перед использованием + отказ от небезопасной объектной десериализации недоверенных данных в пользу схемо-ограниченных форматов + code review перед мержем C) Увеличение частоты релизов D) Отключение HTTPS для ускорения сборки
    Ответ: **B** (Комплекс против A08: подпись всех артефактов, verify перед use, отказ от unsafe object-десериализации в пользу schema-форматов и code review.)

    Ответ: **B** (Недостаточное логирование чаще вскрывается уже после инцидента, когда нужных данных для расследования нет — типичный «post-mortem» discovery A09.)

A) Лог содержит слишком много деталей B) Лог фиксирует только факт «ошибка произошла» без указания, какая именно ошибка, где, с какими параметрами — недостаточно для расследования C) Гранулярность не влияет на полезность лога D) Требуется логировать только успешные операции

38. Почему интеграция threat intelligence фидов с SIEM повышает эффективность алертинга согласно современным практикам A09? A) Threat intelligence не связан с логированием B) Позволяет автоматически сопоставлять внутренние логи с известными индикаторами компрометации (IOC) — IP, хеши, домены — для более быстрого обнаружения известных угроз C) Замедляет обработку логов без пользы D) Требуется только для государственных организаций
    Ответ: **B** (Threat-intelligence feeds сопоставляют логи с известными IOC (IP, хеши, домены) и ускоряют детект известных угроз в SIEM.)

39. Что из перечисленного — пример корректной обработки чувствительных данных при логировании ошибки валидации формы? A) Логировать введённый пользователем пароль в открытом виде для дебага B) Логировать факт ошибки валидации и маскированное/усечённое значение (например, только последние 4 цифры карты), не полное чувствительное значение C) Не логировать ошибку валидации вообще D) Логировать только timestamp без деталей
    Ответ: **B** (При ошибке валидации логируют факт и маскированные/усечённые значения (например, last4 карты), а не полные секреты.)

A) MTTD не связан с логированием/алертингом B) Низкий MTTD напрямую отражает, насколько быстро логирование+алертинг позволяют организации заметить инцидент, что критично для ограничения ущерба C) MTTD измеряется только для инфраструктурных сбоев, не для security D) MTTD не поддаётся измерению
    Ответ: **B** (MTTD показывает, насколько быстро logging+alerting позволяют заметить инцидент; низкий MTTD критичен для ограничения ущерба.)

    Ответ: **B** (Алерт без приоритета, SLA и разбора в очереди тысяч уведомлений — insufficient escalation: детект есть, реакции нет.)

42. Почему пентестерам/red team важно ЯВНО документировать в отчёте, был ли их тест замечен системой мониторинга клиента? A) Не имеет значения для отчёта B) Это прямая проверка эффективности категории A09 самой организации — независимо от того, была ли найдена «классическая» уязвимость C) Красная команда никогда не проверяет мониторинг D) Относится только к blue team
    Ответ: **B** (Фиксация, заметил ли мониторинг red team/пентест, — прямой тест эффективности A09, независимо от найденных «классических» уязвимостей.)

    Ответ: **B** (Изолированное хранилище логов (отдельный account/среда) снижает шанс, что компрометация prod даст доступ и к уничтожению логов.)

    Ответ: **B** (Эффективность A09 проверяют controlled attack (с согласия) и смотрят, заметила ли команда мониторинга за разумное время — purple team.)

46. Почему недостаточно просто «включить логирование» без последующего процесса анализа? A) Достаточно факта включения B) Логи без регулярного/автоматизированного анализа и настроенного алертинга — это просто накопление данных без практической защитной ценности до момента, когда их наконец кто-то просмотрит (часто слишком поздно) C) Логирование само по себе полностью решает задачу обнаружения D) Анализ логов не требует дополнительных ресурсов
    Ответ: **B** (Включённое логирование без анализа и алертинга — лишь накопление данных; защитная ценность появляется только при регулярной/автоматической обработке.)

A) Не является риском B) Увеличивает поверхность для инсайдерской угрозы и вероятность случайной/намеренной модификации или удаления критичных для расследования логов C) Улучшает скорость расследования линейно с числом людей D) Требуется для соответствия всем стандартам

A) Anomaly detection всегда хуже статичных правил B) Позволяет обнаруживать новые, ранее неизвестные паттерны атак, отклоняющиеся от нормального поведения, которые не покрыты заранее прописанными статичными правилами C) Anomaly detection не используется в реальных SIEM D) Не имеет отношения к A09

    Ответ: **B** («Невозможные» состояния со временем становятся возможными; default-ветка с логом/алертом предотвращает тихий пропуск такого случая.)

48. Что из перечисленного — правильный подход к обработке исключения при недостаточных правах доступа к файлу на диске (OS-level ошибка) в приложении?     Ответ: **B** (При ошибке прав на файл: отказать, отдать пользователю безопасное сообщение без пути, залогировать полный server-side контекст.)

49. Почему категория A10 логически «замыкает» список OWASP Top 10:2025, охватывая нештатные условия, которые могут возникнуть в результате эксплуатации ЛЮБОЙ из предыдущих девяти категорий?
