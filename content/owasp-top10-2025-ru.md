# OWASP Top 10:2025 — теория по каждой категории

> 8-е издание, выпущено в ноябре 2025 (первое крупное обновление с 2021). Датасет: ~175k CVE, 589 CWE, данные по 2.8 млн приложений от Bugcrowd, Contrast Security, Semgrep, Veracode, Wallarm и др. Методология: 8 категорий формируются из статистики (incidence rate по CWE в протестированных приложениях + CVSS Exploit/Impact), 2 категории (A03 и A09) добавлены голосованием community survey, т.к. в тестовых данных их сложно обнаружить статистически.

## A01:2025 — Broken Access Control

**Ранг:** #1. 100% протестированных приложений содержали хотя бы один CWE из этой категории — самый частый класс уязвимостей вообще. 40 связанных CWE, наибольшее число occurrences в датасете.

### Теория

Access control — это принудительное применение политики: пользователь не должен иметь возможность действовать за пределами предоставленных ему разрешений. Модель контроля доступа обычно строится на трёх уровнях:
- **Authentication** — кто ты (не входит в эту категорию, см. A07);
- **Authorization** — что тебе разрешено;
- **Enforcement** — где и как это разрешение реально проверяется в коде.

Broken Access Control возникает, когда enforcement либо отсутствует, либо доверяет источникам, которые контролирует атакующий (клиентский код, параметры запроса, скрытые поля, JWT без должной проверки подписи/exp).

Ключевой принцип: access control работает только тогда, когда проверка выполняется в доверенном серверном коде. Любая проверка, реализованная только на фронтенде (скрытие кнопки, disabled-поле, JS-роутинг) — не является контролем доступа, это UX.

### Подкатегории (что относится сюда)

1. **IDOR / BOLA (Insecure Direct Object Reference / Broken Object Level Authorization)** — прямой доступ к объекту по идентификатору (`/api/orders/1234`) без проверки, что объект принадлежит текущему пользователю.
2. **BFLA (Broken Function Level Authorization)** — доступ к административной функции без проверки роли (`POST /admin/users/delete`).
3. **Privilege Escalation** — вертикальная (user → admin) и горизонтальная (user A → данные user B).
4. **Path Traversal** (CWE-22/23/36) — выход за пределы разрешённой директории через `../`.
5. **Force Browsing** (CWE-425) — угадывание/перебор URL без ссылок в UI.
6. **CORS-мисконфигурация** — `Access-Control-Allow-Origin: *` вместе с `Access-Control-Allow-Credentials: true`, или reflect-механизм Origin без валидации.
7. **CSRF** (CWE-352) — принуждение авторизованного пользователя выполнить действие без его ведома (актуально там, где нет anti-CSRF токенов/SameSite).
8. **Metadata tampering** — модификация JWT (алгоритм `none`, подмена `kid`, отсутствие проверки подписи), модификация hidden-полей/cookie для повышения прав.
9. **SSRF** (CWE-918, включена сюда с 2025) — сервер по указке атакующего делает запрос к внутреннему/произвольному ресурсу (metadata endpoint облака, внутренние сервисы, localhost).
10. **Open Redirect** (CWE-601) — используется как primitive для фишинга/обхода allow-list редиректов.
11. **Exposure of sensitive info** (CWE-200/201) — раскрытие данных через отклик API, даже если само действие запрещено (напр., различие 403 vs 404 позволяет энумерацию).

### Как это тестируется (pentest-методология)

- Матрица ролей × эндпоинтов: для каждого privileged-эндпоинта проверять доступ от имени unauthenticated, low-priv, other-tenant пользователя.
- IDOR-фаззинг: последовательный/предсказуемый инкремент ID, замена UUID на чужой (полученный в другой сессии).
- Сравнение поведения UI и прямых запросов (curl/Burp) — то, что скрыто в UI, часто доступно через API.
- Проверка методов: GET защищён, а PUT/DELETE/PATCH на том же ресурсе — нет.
- JWT: `alg=none`, подмена `kid` на путь к файлу (JWK injection), брутфорс HMAC-секрета, отсутствие проверки `aud`/`iss`/`exp`.
- SSRF: инъекция localhost/127.0.0.1, `169.254.169.254` (cloud metadata), DNS rebinding, обход allow-list через редиректы, IPv6/decimal/octal representation IP.
- CORS: отправка произвольного `Origin`, проверка, отражается ли он в `Access-Control-Allow-Origin` вместе с `Allow-Credentials: true`.

### Меры защиты

- Deny by default — доступ разрешён только явно.
- Единая переиспользуемая точка проверки прав (не размазанная по контроллерам).
- Проверка владения записью (record ownership) на уровне domain-модели, а не только на уровне маршрута.
- Rate limiting на чувствительные эндпоинты.
- Инвалидация серверных сессий при логауте; короткоживущие JWT + refresh-токены.
- Логирование отказов авторизации и алертинг на повторяющиеся failures.

## A02:2025 — Security Misconfiguration

**Ранг:** #2 (было #5 в 2021 — самый большой скачок вверх). 16 CWE, средний incidence 3.00%. Рост объясняется тем, что всё больше поведения приложений задаётся конфигурацией (cloud IaC, k8s manifests, feature flags), а не кодом.

### Теория

Это категория про разрыв между «безопасно написанным кодом» и «безопасно развёрнутой системой». Misconfiguration может возникнуть на любом уровне стека: ОС, веб-сервер, application server, база данных, framework, облачные сервисы (S3 buckets, IAM policies), контейнерные оркестраторы.

Типичные проявления:
- Включённые debug/verbose-режимы в production (стектрейсы, debug-эндпоинты типа Django `DEBUG=True`, Spring Boot Actuator без аутентификации).
- Дефолтные учётные записи/пароли, не изменённые после установки.
- Ненужные фичи включены (лишние порты, сервисы, страницы, примеры приложений, ненужные HTTP-методы — TRACE/OPTIONS).
- Отсутствие security headers (CSP, X-Content-Type-Options, X-Frame-Options, HSTS).
- Излишне подробные сообщения об ошибках, раскрывающие stack trace/версии ПО.
- Неправильно настроенные разрешения облачных ресурсов (публичный S3 bucket, чрезмерно широкий IAM).
- Отсутствие security hardening на всех уровнях стека приложения — «out-of-the-box» конфигурация без изменений.
- Несогласованность конфигураций между окружениями (staging vs prod).

### Как тестируется

- Проверка HTTP-методов (OPTIONS/TRACE/PUT/DELETE) на всех эндпоинтах.
- Поиск дефолтных путей: `/actuator`, `/.env`, `/swagger-ui`, `/wp-admin`, `/.git/`, `/console`, cloud metadata.
- Анализ HTTP-заголовков ответа на предмет отсутствующих security headers.
- Форсирование ошибок (некорректный Content-Type, битый JSON) — смотрим, не течёт ли стектрейс/версия фреймворка.
- Инвентаризация облачных ресурсов: публичные бакеты, security groups «0.0.0.0/0», default VPC.
- Проверка версий по баннерам (Server, X-Powered-By) и сопоставление с известными CVE.

### Меры защиты

- Repeatable hardening process, автоматизированное развёртывание (IaC) с baseline-конфигурацией, применяемой одинаково ко всем окружениям.
- Минимальная платформа: убрать неиспользуемые фичи, компоненты, документацию, примеры.
- Регулярный review и обновление конфигураций как части патч-менеджмента (см. A03).
- Сегментированная архитектура (containers/cloud groups/ACL) между компонентами.
- Автоматизированный процесс проверки эффективности конфигураций во всех окружениях (CI-проверки, config-as-code с тестами).

## A03:2025 — Software Supply Chain Failures

**Ранг:** #3 (новая, расширение A06:2021 Vulnerable and Outdated Components). 50% участников community survey поставили её на #1 место — при этом в тестовых данных всего 11 CVE напрямую сопоставлены с CWE категории (сложно тестировать автоматически), но при обнаружении — самый высокий средний incidence rate (5.72%) и самый высокий Exploit/Impact score среди всех категорий.

### Теория

Раньше (2021) категория ограничивалась «известными уязвимостями в компонентах» (по сути — устаревшие библиотеки с публичными CVE). В 2025 scope расширен до всего жизненного цикла supply chain: сборка, распространение, обновление ПО, включая **неизвестные** (не только CVE) компрометации через доверенные каналы.

Компонент (библиотека, framework, образ контейнера, CI/CD раннер, IDE-плагин) в приложении почти всегда исполняется с теми же привилегиями, что и само приложение. Поэтому компрометация зависимости = компрометация приложения.

Признаки уязвимости:
- Не отслеживаются версии всех компонентов (прямых и транзитивных зависимостей), клиентских и серверных.
- ПО устарело/не поддерживается вендором (включая ОС, БД, рантаймы).
- Нет регулярного сканирования уязвимостей и подписки на security bulletins.
- Нет change management для CI/CD, репозиториев кода, артефакторных хранилищ.
- Компоненты берутся из недоверенных источников.
- Нет разделения обязанностей (один человек может закоммитить код и сразу задеплоить в прод без ревью).
- CI/CD имеет более слабую защиту, чем системы, которые он собирает и деплоит.

### Типовые сценарии атак

1. **Компрометация доверенного вендора** — классика: SolarWinds (2019), ~18 000 организаций скомпрометированы через легитимное обновление.
2. **Условно-срабатывающий backdoor** — вредоносный код активируется только при определённых условиях (напр., взлом Bybit на $1.5 млрд в 2025 через supply-chain атаку на кошелёк, срабатывавшую только при использовании конкретного целевого кошелька).
3. **Самораспространяющийся worm в пакетном реестре** — атака `Shai-Hulud` (2025, npm): вредоносные версии популярных пакетов с post-install скриптом, который крал секреты и, если находил npm-токен жертвы, автоматически публиковал заражённые версии её собственных пакетов — червь распространялся сам, поразил 500+ версий пакетов.
4. **Известные уязвимости в компонентах** — Struts2 RCE (CVE-2017-5638, Equifax breach), Log4Shell (CVE-2021-44228).

### Как тестируется

- Построение SBOM (Software Bill of Materials) и сверка с базами уязвимостей (OSV, NVD).
- Анализ транзитивных зависимостей (не только `package.json`, но и весь дерево).
- Проверка целостности пайплайна: кто может мержить/деплоить без ревью, есть ли branch protection, подписаны ли артефакты.
- Проверка происхождения (provenance) артефактов — собраны ли они воспроизводимо, подписаны ли (Sigstore/cosign, SLSA).
- Аудит прав доступа в реестрах пакетов (npm/pypi токены), IDE-расширений.

### Меры защиты

- Централизованный SBOM + непрерывный composition analysis (OWASP Dependency-Track, Dependency-Check, retire.js).
- Пакеты только из официальных источников, предпочтение подписанным.
- Постепенный (staged/canary) rollout обновлений, а не одновременный на всю инфраструктуру.
- Hardening репозиториев кода, воркстанций разработчиков, CI/CD (MFA, least privilege, tamper-evident logs, environment-scoped secrets).
- Мониторинг неподдерживаемых библиотек, план миграции при их обнаружении.

## A04:2025 — Cryptographic Failures

**Ранг:** #4 (было #2 в 2021). 32 CWE, средний incidence 3.80%.

### Теория

Категория про защиту данных in transit и at rest — конфиденциальность и целостность через криптографию. Раньше называлась Sensitive Data Exposure (2017) — переименована в 2021, т.к. exposure это симптом, а cryptographic failure — root cause.

Сначала нужно определить: какие данные требуют защиты (PII, credentials, финансовые, медицинские, business secrets) — согласно применимым законам (GDPR, PCI DSS, HIPAA и т.д.).

Типичные провалы:
- Передача данных в открытом виде (HTTP, SMTP, FTP вместо TLS).
- Использование устаревших/слабых алгоритмов (MD5, SHA1 для паролей, DES/RC4, кастомная «своя» криптография).
- Дефолтные или слабые криптографические ключи, отсутствие их ротации.
- Отсутствие проверки сертификатов, игнорирование ошибок TLS-хендшейка.
- Хранение паролей без соли или с быстрыми хешами (MD5/SHA-256 напрямую вместо bcrypt/scrypt/argon2/PBKDF2).
- Использование initialization vectors (IV) предсказуемо/повторно (ECB mode, статичный IV в CBC).
- Хранение чувствительных данных дольше необходимого, включая кэши/логи/backups.
- Смешение шифрования и кодирования (Base64 воспринимается как «защита»).

### Как тестируется

- Анализ TLS-конфигурации (тестовый сканер типа testssl.sh): версии протокола, cipher suites, наличие HSTS, валидность сертификатов.
- Поиск чувствительных данных в открытом виде: в URL (query string логируется), в localStorage/cookies без флагов Secure/HttpOnly.
- Анализ используемых криптопримитивов в коде/бинарнике (hardcoded keys, weak algorithms).
- Проверка хранения паролей (через утечку БД/дампа, если есть доступ) — формат хешей.
- Проверка padding oracle / bit-flipping для CBC-режимов.

### Меры защиты

- Классификация данных, минимизация хранения того, что не нужно (data minimization/tokenization/truncation).
- Шифрование всех чувствительных данных at rest и in transit современными проверенными алгоритмами и протоколами (TLS 1.2+/1.3, AES-GCM).
- Отдельное управление ключами (KMS/HSM), ротация, разделение ключей и данных.
- Пароли — только через устойчивые к брутфорсу функции с солью (Argon2id, bcrypt, scrypt).
- Отключение кэширования для откликов с чувствительными данными.
- Верификация всех сертификатов и цепочек доверия, отказ от собственных крипто-реализаций.

## A05:2025 — Injection

**Ранг:** #5 (было #3 в 2021). 38 CWE — категория с наибольшим числом связанных CVE. Диапазон от high-frequency/low-impact (XSS) до low-frequency/high-impact (SQLi).

### Теория

Инъекция — это когда недоверенные данные передаются интерпретатору (SQL, ОС-шелл, LDAP, XPath, NoSQL, шаблонизатор, ORM) как часть команды/запроса, и интерпретатор не может отличить данные от кода/структуры запроса.

Root cause — отсутствие разделения между control plane и data plane при построении запроса/команды: конкатенация строк вместо параметризации.

### Подтипы

- **SQL Injection** — классика, включая blind (boolean/time-based), UNION-based, error-based, second-order.
- **NoSQL Injection** — операторы MongoDB (`$where`, `$ne`) через JSON-параметры.
- **OS Command Injection** — передача пользовательского ввода в системный вызов (`exec`, `system`, обратные кавычки в shell).
- **LDAP Injection** — манипуляция LDAP-фильтром.
- **XPath/XML Injection**, включая XXE (хотя XXE частично относится к A08/A05 в зависимости от механизма).
- **Cross-Site Scripting (XSS)** — Reflected, Stored, DOM-based — инъекция в контекст исполнения браузера (HTML/JS/CSS/URL).
- **Template Injection (SSTI)** — инъекция в серверный шаблонизатор (Jinja2, Twig, FreeMarker) → зачастую RCE.
- **Header/CRLF Injection** — инъекция в HTTP-заголовки (response splitting).
- **Command/Expression Language Injection** — OGNL, SpEL (Spring, Struts).

### Как тестируется

- Фаззинг всех входных точек (параметры, заголовки, cookies, файлы, JSON/XML тела) спецсимволами: `' " ; -- <script> {{7*7}} $(whoami)`.
- Дифференциальный анализ откликов (время ответа для time-based blind, разница в контенте для boolean-based).
- Контекстно-зависимый XSS-тест (атрибут/тег/JS-строка/URL — разный payload для каждого контекста).
- Для SSTI — проверка через математические выражения шаблонизатора (`{{7*7}}`, `${7*7}`) и идентификация движка по поведению.
- Статический анализ на конкатенацию строк в запросах к БД/шеллу.

### Меры защиты

- Параметризованные запросы / prepared statements (никогда — конкатенация в запрос).
- ORM с безопасным API вместо ручного построения запросов (но помнить, что ORM тоже можно заставить генерировать инъекцию при неаккуратном использовании).
- Позитивная валидация ввода («server-side input validation», allow-list).
- Контекстно-зависимое экранирование вывода (HTML-entity/JS-escape/URL-escape в зависимости от места вставки в DOM).
- Content Security Policy как defense-in-depth от XSS.
- Ограничение прав учётной записи БД по принципу наименьших привилегий (LIMIT — read-only там, где не нужна запись).

## A06:2025 — Insecure Design

**Ранг:** #6 (было #4 в 2021). Зафиксировано улучшение по индустрии — больше threat modeling и secure-by-design практик, поэтому категория «сползла» вниз в ранге.

### Теория

Это категория про **отсутствующие или неэффективные архитектурные и дизайн-контроли** — в отличие от Security Misconfiguration (плохо настроенный правильный контроль) или Injection (плохая реализация правильной идеи), Insecure Design — это когда дизайн сам по себе не предусматривает нужный контроль, даже при идеальной реализации.

Пример разницы: если приложение не проверяет CAPTCHA/rate-limit при массовой покупке лимитированного товара (бизнес-логика позволяет боту скупить весь сток) — это провал дизайна, а не бага реализации.

Ключевые концепции:
- **Threat modeling** должен выполняться на этапе проектирования, не после релиза.
- **Secure design patterns** и reference architecture, переиспользуемые между проектами.
- **Business logic abuse** — злоупотребление легитимным функционалом не по назначению (например, endless refund loop, race condition в накрутке баллов лояльности, обход лимитов через параллельные запросы).
- Разделение trust boundary на уровне архитектуры (tier separation).
- Insecure design нельзя исправить патчем — только пересмотром архитектуры.

### Как тестируется

- Формальный threat modeling (STRIDE, PASTA, attack trees) как этап пентеста, а не только техническое сканирование.
- Тестирование бизнес-логики: гонки состояний (race conditions) при одновременных запросах (например, двойной вывод средств через параллельные запросы на списание).
- Проверка лимитов бизнес-процессов (может ли пользователь обойти количественные ограничения — купоны, лимиты запросов, промокоды).
- Abuse-case тестирование, а не только happy-path.

### Меры защиты

- Secure development lifecycle с threat modeling для критичных user story/фич на этапе дизайна.
- Библиотека переиспользуемых secure design паттернов и защитных компонентов (auth, rate limiting как сервисы).
- Unit- и integration-тесты, покрывающие ключевые атакующие сценарии (не только позитивные тест-кейсы).
- Сегрегация tier-ов по уровню доверия и данных.
- Ограничение потребления ресурсов на уровне пользователя/сервиса, транзакции и API (rate limiting как часть архитектуры, не заплатка).

## A07:2025 — Authentication Failures

**Ранг:** #7 (без изменений). Переименована из «Identification and Authentication Failures» — точнее отражает объединённые 36 CWE. Индустрия стала лучше за счёт стандартизированных фреймворков аутентификации (OAuth2/OIDC, готовые Identity Provider'ы вместо самописной аутентификации).

### Теория

Подтверждение личности пользователя (identity) может быть ослаблено из-за:
- Разрешения брутфорс-атак и credential stuffing (нет rate limiting/lockout/CAPTCHA).
- Разрешения слабых, дефолтных или широко известных паролей («Password1», «admin/admin»).
- Слабых процессов восстановления пароля/секретных вопросов, предсказуемых токенов сброса.
- Хранения паролей в открытом виде/слабо хешированными (пересечение с A04).
- Отсутствия или слабой multi-factor authentication.
- Раскрытия session ID в URL (`;jsessionid=`), отсутствия ротации session ID после успешного логина (session fixation).
- Некорректного тайм-аута/невалидации сессий, особенно на shared/public компьютерах.

### Как тестируется

- Проверка политики паролей, наличия rate limiting/lockout на login/forgot-password эндпоинтах.
- User enumeration через разное поведение (сообщение об ошибке, время ответа) при существующем/несуществующем логине.
- Session fixation: устанавливается ли session ID до логина, меняется ли после.
- Проверка предсказуемости/энтропии токенов сброса пароля, session ID.
- Проверка обхода MFA (race condition, отсутствие проверки MFA-статуса на бэкенде, downgrade-атаки).
- OAuth/OIDC misconfig: открытый redirect_uri, отсутствие проверки state-параметра (CSRF в OAuth flow), PKCE отсутствует для public client.

### Меры защиты

- MFA для доступа к чувствительным функциям, где это возможно.
- Не деплоить дефолтные учётки, требовать смену дефолтных паролей.
- Реализация NIST 800-63b рекомендаций по паролям (длина важнее сложности, проверка по спискам скомпрометированных паролей).
- Rate limiting и учёт неудачных попыток с прогрессивными задержками/lockout без раскрытия деталей причины отказа.
- Server-side, безопасное управление сессией: случайный session ID высокой энтропии, инвалидация после логаута/по таймауту, ротация после привилегированных действий.

## A08:2025 — Software or Data Integrity Failures

**Ранг:** #8 (без изменений).

### Теория

Категория про отсутствие проверки целостности при работе с кодом и данными, где приложение доверяет источнику/содержимому без криптографической верификации. Отличие от A03 (Supply Chain): A08 — это integrity failures на уровне конкретного артефакта/данных (ниже уровнем), тогда как A03 — про весь процесс сборки/поставки экосистемы.

Ключевые сценарии:
- **Insecure deserialization** — десериализация недоверенных данных без валидации типа/структуры может привести к RCE (Java, PHP, Python pickle, .NET BinaryFormatter).
- **Отсутствие проверки цифровой подписи/хеша** при auto-update механизмах (плагины, обновления ПО подтягиваются с CDN без проверки подписи).
- **CI/CD pipeline без должного контроля целостности** — возможность внедрить неавторизованный код, который затем считается доверенным.
- Использование недоверенных плагинов/библиотек/CDN без Subresource Integrity (SRI) для клиентского JS.

### Как тестируется

- Поиск точек десериализации (Java `ObjectInputStream`, PHP `unserialize()`, Python `pickle.loads()`) и проверка возможности инъекции вредоносного объекта (gadget chains — ysoserial и аналоги).
- Проверка загружаемых с внешних CDN скриптов на наличие SRI-хешей (`integrity=`).
- Анализ auto-update механизмов: проверяется ли подпись/хеш перед установкой обновления.
- Ревью CI/CD на предмет неподписанных артефактов, возможности подмены на этапе между сборкой и деплоем.

### Меры защиты

- Использование цифровых подписей для верификации происхождения ПО/данных.
- Проверка, что зависимости и файлы приходят из ожидаемых репозиториев через verified/signed channel.
- SRI для сторонних скриптов, CSP для ограничения источников исполняемого кода.
- Не использовать десериализацию недоверенных данных вообще, либо использовать безопасные форматы (JSON без исполняемого кода) с строгой схемой валидации; изоляция/sandbox для процессов десериализации, если избежать нельзя.
- Обязательное code review перед мержем в pipeline, отсутствие возможности деплоя без прохождения проверок.

## A09:2025 — Security Logging & Alerting Failures

**Ранг:** #9 (без изменений). Переименована из «Security Logging and Monitoring Failures» — акцент сдвинут на **alerting**, потому что логирование без срабатывания реакции бесполезно для обнаружения инцидента.

### Теория

Без достаточного логирования и мониторинга инциденты не могут быть обнаружены. Категория традиционно недопредставлена в автоматизированных тестовых данных (сложно тестировать «отсутствие лога» сканером) — поэтому попадает в Top10 через community survey, а не только через статистику.

Признаки недостаточности:
- Аудируемые события (логины, неудачные попытки логина, отказы доступа, серверные ошибки высокой значимости) не логируются.
- Предупреждения и ошибки генерируют логи с недостаточным контекстом для forensics (нет user id, timestamp, IP, trace id).
- Логи хранятся только локально, без централизации (SIEM), без защиты от подделки/удаления атакующим.
- Отсутствует эффективный alerting/пороги для аномалий в реальном времени — обнаружение инцидента занимает недели/месяцы вместо часов.
- Приложение не способно обнаружить, эскалировать или сигнализировать об активной атаке в реальном времени.

### Как тестируется

- Проверка, генерируются ли логи при неудачных попытках логина, отказах авторизации, вводе явно вредоносных payload'ов (SQLi/XSS попытки).
- Проверка возможности внедрения log injection (CRLF в поля, попадающие в лог, для подделки записей).
- Оценка полноты контекста в логах (можно ли по логам восстановить цепочку событий инцидента).
- Проверка защиты логов от модификации/удаления с правами приложения (пишет ли компрометированный процесс в append-only/централизованное хранилище).

### Меры защиты

- Логирование всех событий, связанных с аутентификацией, контролем доступа, валидацией ввода на стороне сервера, с достаточным контекстом для forensics, но без записи чувствительных данных (пароли/токены) в открытом виде.
- Централизация логов в SIEM с настроенным alerting и эскалацией.
- Формат логов, устойчивый к log injection (структурированное логирование, экранирование).
- Playbook и regular drills для incident response (см. NIST 800-61r2).
- Мониторинг DAST-сканирования/пентестов — приложение должно генерировать заметные алерты во время активного тестирования (если алертов нет — сам этот факт сигнализирует о провале мониторинга).

## A10:2025 — Mishandling of Exceptional Conditions

**Ранг:** #10 (новая категория). 24 CWE, наибольшая средняя coverage тестируемости (37.95%) среди новых/малых категорий, но при этом относительно низкий средний incidence (2.95%) — зато огромное число total CVE (3416) и occurrences (769k), потому что покрывает очень широкий спектр языков/платформ.

### Теория

Ранее часть этих CWE относили к «poor code quality» — в OWASP посчитали формулировку слишком общей и выделили конкретный фокус: **как система ведёт себя, когда происходит что-то нештатное**.

Три типа провала обработки нештатной ситуации:
1. Приложение **не предотвращает** возникновение нештатной ситуации (нет валидации входа, нет лимитов).
2. Приложение **не обнаруживает** её в момент возникновения (ошибка проглатывается — `catch (Exception e) {}`).
3. Приложение **реагирует некорректно** уже после того, как ситуация произошла (fail open вместо fail closed, частичный откат транзакции).

Причины: отсутствующая/неполная валидация ввода, обработка ошибок «на верхнем уровне» вместо места непосредственного возникновения, неожиданные состояния окружения (память, привилегии, сеть), несогласованная обработка исключений в разных частях кодовой базы, необработанные исключения вообще.

Может проявляться как: логические баги, переполнения, race conditions, мошеннические транзакции, проблемы с состоянием/ресурсами/таймингом/аутентификацией/авторизацией.

### Ключевые CWE

- CWE-209/CWE-550 — сообщение об ошибке содержит чувствительную информацию (стектрейс, версии, внутренние пути) → используется атакующим как разведка для построения более точной атаки (напр., детализированной SQLi).
- CWE-636 «Not Failing Securely (Failing Open)» — при ошибке система по умолчанию **разрешает** действие вместо того, чтобы **запретить** (например, при сбое проверки прав доступа система пропускает пользователя вместо блокировки).
- CWE-703/754/755 — общая improper handling/check нештатных условий.
- CWE-476 NULL Pointer Dereference — сбой из-за необработанного null → крэш/DoS, иногда — обход последующей логики.
- CWE-234/235 — пропущенные/лишние параметры не обрабатываются корректно.
- CWE-369 Divide By Zero — как класс необработанного арифметического исключения.

### Типовые сценарии атак

1. **Resource exhaustion (DoS)** — приложение ловит исключение при загрузке файла, но не освобождает ресурс после ошибки; повторные ошибки исчерпывают доступные ресурсы (file handles, соединения, память).
2. **Sensitive data exposure через ошибки БД** — полный текст ошибки БД показывается пользователю; атакующий намеренно форсирует разные ошибки, чтобы собрать структуру запроса/схему для более точной SQL-инъекции.
3. **State corruption в многошаговой транзакции** — атакующий обрывает сетевое соединение посреди транзакции (списание → зачисление → лог); если система не откатывает всю операцию при сбое (fail closed), возможен race condition, позволяющий отправить средства несколько раз или обнулить баланс некорректно.

### Как тестируется

- Форсирование ошибок нестандартным вводом (некорректный Content-Type, обрыв соединения посреди multipart-запроса, edge-case значения: `null`, пустая строка, отрицательные числа, переполнение буфера, экстремально длинные строки).
- Проверка сообщений об ошибках на утечку внутренней информации (стектрейсы, пути, версии библиотек, SQL-запросы).
- Тестирование race conditions в многошаговых операциях (параллельная отправка одного и того же запроса — списание средств, применение промокода, лимитированная покупка).
- Проверка поведения при недоступности зависимого сервиса (fail open vs fail closed) — что происходит с авторизацией, если сервис проверки прав недоступен?
- Load/stress-тестирование на предмер resource exhaustion через накопление необработанных исключений.

### Меры защиты

- Обработка исключений в месте их возникновения (не «выше по стеку» общим catch-all), с полноценной обработкой (лог + алерт + понятная пользователю ошибка без внутренних деталей).
- **Fail closed**, а не fail open: при сбое многошаговой операции — полный откат.
- Централизованная (единая для всего приложения) стратегия обработки ошибок/логирования/алертинга, а не разные подходы в разных модулях.
- Rate limiting, resource quotas, throttling — превентивно, чтобы не допускать нештатные условия вообще.
- Строгая input-валидация с санитизацией на входе.
- Threat modeling и код-ревью конкретно на предмет обработки ошибок; stress/penetration-тестирование финальной системы.
